# Agent 运行分析与可靠性：设计及开发路线

日期：2026-10-13。此文是方案，不代表四个方向已经实现。用户选择本轮先梳理设计与开发路线；先前生成的运行分析代码只作为现状原型参考，不继续扩展功能。

## 1. 产品定位与范围

把研究工作台扩展为能够回答三类问题的运行分析工具：这次为什么失败；改动后哪些固定任务退化；资源花在哪里。执行沙箱负责保障这些执行的边界。

第一版服务现有项目的主对话与专家任务，不承诺接入任意外部 Agent 框架。先完成真实运行 → 保存证据 → 回放 → 固定任务复测 → 结果对比的完整闭环，之后才考虑外部轨迹导入。

沿用成熟产品的 trace/observation 与 dataset/experiment 模式：[Langfuse 数据模型](https://langfuse.com/docs/observability/data-model)、[实验对比](https://langfuse.com/docs/evaluation/experiments/compare-experiments)。采用模式，不要求引入额外服务或重建现有 PostgreSQL 账本。

## 2. 当前基础与缺口

| 方向 | 已有基础 | 核心缺口 |
| --- | --- | --- |
| 轨迹与归因 | RunRecord、CoreEvent、StoredRunEvent，受控 operation 与模型 manifest；Flow 表示任务关系 | 模型、检索、工具未统一成可比较的执行步骤；事实归因与语义假设需要分开 |
| 回归评测 | 八道 research_quality 固定题，冻结源码/规则/模型/预算，候选方法 A/B，独立评分证据 | 当前 A/B 只比较 expert_synthesize 方法指令；尚无通用 prompt/skill 变更回归、主助手端到端套件和质量放行门槛 |
| 成本与延迟 | operation 用量含失败/摘要/重试，部分模型 duration，评测执行/整体延迟 | 计费单价未冻结；工具/等待/保存耗时覆盖不全；缺失值和范围需要统一 |
| 权限与沙箱 | scope 授权、固定仓库与允许路径、独立 worktree、可信测试配置、受控工具调用 | worktree 不隔离进程；可信测试命令仍可能执行被 Agent 修改的代码；没有 OS 级网络、密钥与资源隔离 |

先前原型已经展示主对话/专家事件回放、失败事件、用量及粗粒度对比，但没有输入输出内容差异、完整语义归因或真实沙箱，不应据此宣称可靠性平台已完成。

## 3. 轨迹回放与失败分析

### 数据设计

现有账本继续作为事实来源。新增测量写入现有执行边界，不另建一套运行身份或观测数据库。

- 运行：run_id、parent_run_id、agent 身份、所属研究/任务、状态、冻结输入及方法/skill 版本引用。
- 步骤：operation_id、parent_operation_id、类型、工具/模型名、attempt、开始/结束时间、实测 duration、状态、错误码、用量完整性。
- 类型先覆盖模型请求、工具调用、委派；检索由实际检索工具及证据读取记录识别，规划由实际规划运行识别。不能仅凭事件名称推断推理过程。
- 同一执行步骤恢复时沿用同一 operation_id；真实重新请求用新 attempt/operation_id，保存关联。去重规则用于计量，不掩盖真实重试。
- 正文通过现有工件引用按需读取，不复制到指标表。概览默认不返回原始参数、环境变量、provider body 或密钥；正文读取独立验证当前授权并脱敏。
- 新记录写完整测量，旧记录保留未知，不通过迁移或猜测补齐不存在的证据。

### 页面设计

Flow 继续表示任务关系；点击某次运行打开步骤树和时间线。选择步骤查看已授权的输入引用、结果引用、状态、错误和测量。回放只重放显示状态，不重新执行工具。

归因分两层：

1. 确定事实：哪次调用报错、参数校验失败、授权拒绝、超时、上下文超限、结果契约失败；给出具体步骤和错误证据。
2. 待核查假设：是否检索遗漏、证据过时、计划依赖错误、工具选择不当；必须关联原文/工具结果/预期答案，允许 unknown，不根据失败节点自动断言根因。

成功运行中的工具失败属于恢复事件。最早失败不必然是最终失败的原因。

两次运行以逻辑步骤身份和调用关系对齐，显示新增/删除/状态变化、工具参数及结果的授权内容差异。不能按第 N 步机械配对，因为一次新增工具调用会让后续序号偏移。

## 4. 回归测试框架

继续使用现有 research_quality 的 plan/run/report，扩展其冻结清单和比较报告，不另写评测 Runner。

第一层仅完成现有方法指令 A/B 的正式回归门槛。下一层再支持 skill 版本与主助手 prompt；每个实验只改变一个被明确登记的变量。版本由实际加载内容哈希确定，不能仅记录 Git commit，因为当前仓库可能有未提交修改。

每个案例固定：输入/资源版本、期望产物或 rubric、允许工具与网络、预算、评分器版本。执行证据关联真实 run_id，报告能跳到失败轨迹。

增加四类案例：正常研究任务、曾发生的真实失败、边界/冲突输入、权限与不可信资料攻击。真实失败脱敏后固化；八道现有题继续是开发回归集，不冒充独立泛化测试。

比较分三栏：产物正确、正常执行、资源消耗。失败、中断和待审保留在分母；语义待审不算通过。先做机器可验证的格式、数值、来源版本和授权检查，再保留独立人工语义评审。后续如果引入模型裁判，先用已人工评分样本校准，裁判自身版本与费用也需冻结。

质量门槛在跑候选前确定：关键权限项不能失败；关键案例已确认的正确性不能退化；未评语义则整批 pending。普通质量项和 token/延迟允许变化多少由任务目标与基线波动确定，不凭空统一设百分比。

比较命令返回通过/失败/待定，并映射为可被 CI 区分的退出码。默认 CI 运行确定性契约测试；真实模型批次显式启动且限制总预算，不在普通提交时自动触发收费。

## 5. 成本与延迟分析

计量单位是实际 provider operation。汇总不能同时叠加 operation 与 RunResult 的同一份 token；父子 Agent 也按唯一 operation 去重。输入 token 已含缓存，不再次加缓存数。

展示运行/Agent/步骤三个层级：请求次数、输入/缓存/输出 token、已知费用、模型服务时间、工具时间、总墙钟时间与排队/保存时间。并发步骤总和不能替代总墙钟时间。

计费规则按 provider + 实际模型 + 生效时间冻结，输入、缓存、输出各自计价，明确币种；已知使用量 × 当次冻结单价得到估算费用。没有覆盖单价或用量不完整则费用 unknown，已知部分单独展示。供应商账单另行核对，不能称估算为账单金额。

第一版“浪费”只输出可检查线索：重复读取同一内容、完全相同的工具请求、长输入短产物、连续参数修复、摘要/辅助请求占比异常。只有判断额外调用没有带来有用新证据后才能称为可节省开销，不能把失败重试或大 token 自动等同于浪费。

## 6. 执行沙箱与权限

保留应用授权和受控 broker：Agent 选择能力与允许路径，身份、权限和可信测试命令由宿主决定。沙箱提供第二道执行边界，不能替代 scope 检查。

优先把“运行被 Agent 修改过的代码/测试”移到独立 Linux worker 的每任务容器，复用成熟容器运行时；macOS 开发环境通过容器 VM 验证同样边界。实际部署平台确认后只实现一个后端，不先做通用多沙箱抽象。

任务容器只取得指定代码快照与临时输出目录；不挂载宿主 HOME、私有资料目录、数据库凭据、模型密钥或 Docker socket。默认无网络，工具联网由宿主 broker 按权限执行，模型请求也由 broker 持有凭据。需要依赖的测试使用预构建并固定摘要的镜像，不在任意任务内联网安装。

配置非特权用户、只读根文件系统、移除不需要的 capabilities、禁止提权、CPU/内存/PID/时间/输出上限；执行结束先验证交付，再回收容器。Docker 默认不设置资源上限，必须显式配置，参见 [资源限制](https://docs.docker.com/engine/containers/resource_constraints/)和 [安全模型](https://docs.docker.com/engine/security/)。

越权读写、链接逃逸、密钥探测、外网连接和资源耗尽都用专用攻击夹具验证。执行 rm -rf 只能影响任务临时目录；宿主哨兵文件和未授权目录必须保持完整。拒绝与超时事件进入轨迹，回归集复用这些攻击案例。

接受外部不可信代码之前，沙箱验收是前置条件。即使产品页面尚未提供沙箱概览，也不能以完成可视化为由延后这条安全门槛。

## 7. 分阶段交付与验收

| 阶段 | 交付物 | 完成标准 |
| --- | --- | --- |
| M0 证据契约 | 指标口径、运行/步骤身份、未知与授权规则、固定验收夹具 | 正常/失败/取消/强杀恢复各能明确哪些事实已知；费用和延迟口径不混淆 |
| M1 轨迹完整闭环 | 实际模型/工具/委派测量，运行步骤树、时间线、事实归因 | 从失败运行定位到具体调用及可读证据；成功恢复不过度归因；撤权后不可读；真实 PostgreSQL + SDK 验证 |
| M2 回归闭环 | 现有方法 A/B 门槛、案例级报告与轨迹链接，再扩展 prompt/skill 版本 | 故意注入退化能定位具体案例且比较命令阻断；待审不放行；基线/候选不影响产品库 |
| M3 成本诊断 | 冻结单价、分层费用/延迟、重复与辅助调用线索 | 计量去重，缓存不重计；失败和恢复保留未知；样例能与供应商用量对账 |
| M4 沙箱验收 | 单一实际平台的隔离执行器、任务权限摘要、攻击回归集 | 未授权宿主读写/密钥/网络受限，资源耗尽受控；代码交付仍通过原固定审核链路 |

M0 → M1 → M2 → M3 为产品闭环顺序。M4 可以单独准备，且必须在开放不可信代码执行前通过。每阶段都形成可使用的版本；上一阶段验收未通过，不继续堆功能。

不先安排自定义观测查询语言、跨框架 SDK、自动根因 LLM、通用 DAG 编辑器、自动修复 Agent 或多种沙箱后端。每个新能力都应由现有闭环暴露的具体需求驱动。

## 8. 展示与面试证据

准备一个可重复的演示：固定任务失败 → 回放定位证据 → 修改一个方法/skill 版本 → 同一固定任务集复测 → 展示修复与未退化案例 → 查看 token/延迟 → 展示越权测试被隔离。代码改动可用，但报告仍要区分确定性夹具、真实模型结果与未完成语义评审。

每阶段留三样产物：运行证据、固定回归报告、简短架构与边界说明。面试中的结论限定到实际测试范围，而不是声称所有 Agent 团队都需要或已经解决全部可靠性问题。
