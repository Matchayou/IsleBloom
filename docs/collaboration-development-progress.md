真实模型消息链路已通过：`collaboration-c2-message-verification.json` 记录主助手向已有专家会话发送普通追问、专家关联回复、主助手转述；新增专家消息 2 条，新增正式运行 0 个，任务数未变。第一次尝试失败及可观察证据见 `collaboration-c2-message-attempt-1.json`；补齐专家目录中的任务 ID 后复测成功。该失败的精确工具参数未持久化，原因判断为推断。

补充：运行中任务的修订等待旧运行结束，新版本的运行上限按任务版本计算；测试覆盖 v1/v2/v3 连续执行。消息现在分开记录已投递与已消费：普通信息进专家会话时为 `delivered`，下一次专家讨论完成后与消费该消息的回复 ID 一起原子保存；提问在取得回复后标为 `consumed`。取消请求持久化并在恢复派发之前处理；同一命令重试不会新增取消，运行中的请求先显示 `stopping`，运行终止后才显示 `cancelled`，迟到模型输出不能作为成功结果发布。主助手的 `cancel_task` 和专家页“请求停止”接通此路径；直接用户修订经 `/api/expert_revise` 使用相同版本化服务，可仅保存或等当前运行结束后执行。内存与 API 测试已通过；独立 PostgreSQL 协作套件 21/21 通过，包含重启后先恢复取消再派发。完整回归在取消路径修正后 227 通过、171 跳过；新增的运行中取消竞态测试单独通过。

取消后替换语义已接通：`revise_task(mode="replace")` 为旧版本记录取消请求，在旧运行结束前保留排队状态；旧版本的迟到输出保存为失败，新版本随后单独执行。确定性竞态测试验证两个版本和两次模型调用均可追溯；专家页提供相同操作。

后续补上了获准专家间一次提问及正式子任务派发。专家工具只能访问经理在固定交接记录中批准的协作者；子任务输入只能是父任务固定输入的子集，记录 `parent_task_id`，不会自动形成专家互相回复循环。`cancel_task(include_children=true)` 现在为现有后代写入停止请求，恢复循环依次处理；新建的迟到后代也会因祖先停止而拒绝执行。后台完成的专家结果在主助手已经先回复时，会触发有聊天版本检查的自动续接；同一批两个结果只续接一次。若新用户消息已到达，结果留待新回合输入，不覆盖用户的新问题。结果回复与通知确认在同一事务中提交。

主助手可从专家会话目录中选择特定消息片段，交接包固定会话 ID、消息 ID、发送者、任务版本与其资料/结果引用。执行前重新验证该会话、原任务和来源权限；撤权后不能继续读取交接。`test_expert_discussion_excerpt_is_frozen_with_its_session` 以信息消息、正式下游任务和撤权验证该路径。

普通补充消息现可携带同一主任务中获准的新增资料与结果引用。专家下一次讨论时读取保存的正文/结果，并标明待复核状态；这些内容保持讨论材料身份，不会偷偷改写正式任务版本。消息保存后的撤权会阻止继续披露；确定性测试覆盖正文进入讨论输入、正式任务输入未变及撤权拒绝。

新增持久 `ManagerNotice`：用户在专家页直接讨论、修订或取消时，通知与原操作在同一事务保存；后台以主对话版本检查续接，主助手回复与通知确认同事务提交。未能立即续接的通知留待下一用户回合，固定输入中显式提供通知内容。内存测试 `test_user_expert_discussion_notifies_manager_once` 和专用 PostgreSQL 重开测试验证持久性与一次确认。8783 真实模型案例中，用户向专家连续发送讨论消息后，主助手自动说明任务未变、失败及待复核状态；浏览器无需手动刷新即出现回复。专家页已在浏览器检查对话主体、任务详情、右侧来源、切换及刷新后草稿保留。

专家主动索要信息的缺口现已完成：`request_manager_information` 保存问题和已完成工作，暂停专家的当前工具对话，交给主助手检查当前主任务的对话和资料。主助手有信息时显式选择来源，校验后授权给同一任务/运行；没有或只有部分信息时，专家停止索要，依据已有信息完成并在报告、missing 和回执中保留缺口。原任务版本不变，补充授权另有持久记录。每个运行只允许一轮汇总提问，重复调用返回原答复。主助手模型无法完成检查时也明确记录原因并让专家继续，不伪装成已经查明资料不存在。

正常运行沿同一次 SDK 工具对话继续；进程重启时从固定输入、保存的进度及原答复重建继续执行，不宣称逐 token 恢复未保存的模型内部状态。等待与答复记录、专家会话消息、回复关联和主助手通知存入 PostgreSQL；已答复后恢复不会再次调用主助手，也不会新建任务版本或专家运行。恢复中的主助手调用最多两次，未确定的前次用量标为不完整。取消、换版本及撤权均阻止迟到答复继续发布；未读或外部来源不能授权。

## C4：并行、依赖与获准协作 — 进行中

获准协作者可以回答专家的一次问题，也可接收其正式子任务。测试覆盖跨主任务或未授权会话拒绝、子任务父关系、固定输入边界、祖先取消传播，以及两个后台任务汇总后只生成一条经理回复。失败的后台运行保留 `rework` 回执并通知主助手说明没有可信结论；同步拿到结果的经理回合会原子确认通知，避免重复回复。独立 PostgreSQL 协作套件最近一次为 30/30 通过；完整回归为 237 通过、173 跳过。8783 独立预览重启后仍显示 C3 历史对话及真实任务 Flow，8771/8782 原实例保持运行。

另以 `scripts/verify_collaboration_c4_flow.py` 在隔离的 8783 数据库中生成明确标为 synthetic 的四任务 Flow。`collaboration-c4-flow-verification.json` 固定四个任务、已复核结果依赖、专家消息及完成状态；浏览器实际打开该项目，确认“结果依赖”“子任务”“协作消息”三类连线均来自任务活动接口并呈现在同一画布。此案例只验证业务/UI 连线，不作为真实市场结论或真实模型多专家决策的证据。

未来依赖现可在 `delegate_task(upstream_task_ids=...)` 建立等待意图及临时依赖边。恢复循环仅在指定上游任务版本取得独立复核 `passed` 回执后，生成新的固定交接包和下游任务版本；上游失败、取消或未执行即被新版本取代时，下游明确失败。等待态不能手动执行，Flow 标记“等待复核”。内存测试、专用 PostgreSQL 关闭/重开测试均通过；另修正“别的版本已有运行，却把原版本一直留在等待态”的边界。

主任务现在汇总并限制专家任务数 8、委派深度 2、累计预留模型轮次 80、已记录 tokens 300,000；不确定用量显式列出，但允许在任务数和轮次上限内继续补做，DBOS 队列最多并行 2 项。按用户最新确认，C4 当前设计不设金额上限；完整 USD 费用预算不再是完成门槛。现有执行限制和用量记录继续保留，不代表美元费用上限。

[C4 真实模型合成案例](collaboration-c4-live-verification.json)使用两名不同专家并行审查两份明确虚构的口径。主助手实际调用专家目录、上下文读取和两次派发；综合专家交付 `pending_review`，搜索专家因 `Tool input is not JSON` 失败并产生 `rework` 回执。主助手续接明确记录一侧失败、一侧待复核，说明 12% 与 21% 口径不可比且均不可正式采用。此证据通过“部分失败不被隐藏”，不满足“两份成功专家结果的分歧裁定”。后续直接专家讨论的主助手自动续接也在同项目中验证。
