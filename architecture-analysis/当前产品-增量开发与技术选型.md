## 1. 文档定位与当前结论

本文将[现版产品设计](./产品设计-当前版本.md)转成开发顺序、模块边界、技术选择和验收门槛。它是后续开发入口；[原增量开发文档](./增量开发架构与阶段验收.md)保留历史阶段定义和技术细节，[阶段验收流程](../docs/development-acceptance-process.md)继续适用。发生冲突时，以现版产品需求及本文的新计划为准，不用新要求改写历史验收结论。

产品核心闭环是：**统一聊天 → 主助手拆任务 → Jev 选择专家与模型 → 专家独立并发研究 → 检查并交接结果 → 从消息分支探索 → 选择性带回主线 → 用户继续决策。** 专家方法在有评测依据后独立改进。

本次核对了产品文档、旧阶段规划、README、Stage 4 验收记录、依赖清单，以及路由器、模型适配器和装配入口的局部源码。未重跑历史测试，未进行全仓库审计。下文“已有”表示有对应实现或历史验收依据，不表示最新需求已经通过。

### 1.1 六个必须分清的概念

| 概念 | 管理什么 | 不应混同 |
|---|---|---|
| 主线/分支 | 用户持续探索的目标、消息、输入与成果 | 后台每次专家调用 |
| 专家定义 | 职责、方法、工具契约、评价标准 | 某个固定模型或永久进程 |
| 专家任务 | 某个目标和任务单版本、独立上下文 | 专家的全部历史记忆 |
| 执行运行 | 一次实际尝试、模型配置、用量与错误 | 任务本身；重试不能清空任务预算 |
| 结果与交接 | 不可变产物、回执、检查和选定引用 | 自动覆盖父摘要或合并所有聊天 |
| 方法进化 | 候选经过评测后发布新版本 | 每次反馈立即修改线上方法 |

首批采用四种能力：搜索、提取、分析校验、综合探索。它们是起始开发配置，不固定产品永远只有四位专家。主助手负责组织任务，Jev 负责有限候选选择，程序负责权限、预算、版本和执行控制。

### 1.2 已有基础与关键差距

| 能力 | 已有依据 | 当前设计还需补齐 |
|---|---|---|
| Agent 执行 | Core、SDK adapter、显式独立输入；Stage 0 记录 | 专家方法与实际模型配置的任务级绑定 |
| 持久记录 | Ledger、PostgreSQL、原子提交、幂等和保存重试 | 将任务单、回执、检查和路由记录接入同一业务提交边界 |
| 并发 | Dispatcher、结果收集、失败/取消和组预算 | 当前 router 是显式成本/速度/限制三专家；尚非 Jev 自动选择 |
| 资料隔离 | ResourceService、ScopeService、ContextBuilder、解析/OCR | 任务交接的必需/可选输入、对 Jev 的外发范围；普通财报字段核验 |
| 联网 | 对批准 URL 目录有界查询与抓取 | 通用搜索发现尚未完成；不得把 URL 目录查询称为全网搜索 |
| 研究节点 | 固定结果版本、父挂载、比较、排除、React Flow 页面 | 以聊天为中心、从消息分叉、持续对话、选择片段回传及采用记录 |
| 引用 | 资料定位与输入版本基础 | 结论级证据支持、点击原文属于 Stage 5 |
| 长任务/进化 | 旧规划有设计 | 跨进程恢复、评测产品化、方法发布与进化尚待实现 |

依据：[README](../README.md)、[Stage 4 验收](../docs/stage-4-acceptance.md)、[现有路由器](../src/agent_core/orchestration/router.py)、[模型适配器](../src/agent_core/adapters/openai.py)。

## 2. 分层架构与数据所有权

```text
聊天界面 / 分支导航 / 结果与引用面板
                   ↓
主助手协调：目标、任务单、依赖计划、交接与汇总
                   ↓
应用服务：任务 / 分支 / 路由 / 检查 / 提交
        ↙          ↓                  ↘
资料与作用域    Jev 决策适配器       Dispatcher
上下文装配     候选目录与规则          ↓
        ↘                       ExecutePort → Core → Agents SDK
                   ↓
Ledger + 业务仓库（PostgreSQL）/ 原始资料与解析文件
```

模型调用期间不持有数据库事务。Jev、数据库、解析和持久执行的依赖不进入 Core。业务模块通过公共服务/仓库端口协作，应用层负责跨模块提交；禁止某个模块绕过服务修改另一个模块的私有表。

| 所有者 | 数据与职责 | 复用位置 / 计划扩展 |
|---|---|---|
| execution | run、事件、用量、保存状态 | 复用 `execution/`、`app/commits.py` |
| research | 分支目标、消息锚点、结果版本、依赖、回传与采用 | 扩展 `research/`，不另建一套竞争的研究树 |
| resources/context | 原文件、来源快照、解析版本、授权范围、只读挂载、实际读取 | 复用 `resources/`、`context/` |
| tasks（新增） | 专家任务单版本、交付回执、检查记录 | R1 才创建；与 execution/research 通过应用事务结合 |
| routing（新增） | 候选目录、两步决策、规则排除、固定模型配置 | R2 才创建；复用既有 Dispatcher，不添加第二个执行循环 |
| evidence（新增） | 结论、证据片段、支持关系和引用检查 | Stage 5，引用现有来源版本 |
| evaluation/methods（后续） | 数据集、反馈、方法版本、候选与发布 | Stage 7–10 逐层增加 |

名称用于划分责任，不要求每个概念都立即拆成服务或数据库表。先用清晰模块和现有数据库；不预建消息总线、插件市场、通用工作流 DSL 或多租户平台。

### 2.1 需要固定的最小契约

- **TaskSpec**：稳定任务 ID、所属分支、版本、用户目标、约束、专家/方法版本、输入引用、交付格式、编号验收项、依赖与预算。路由前是草案，派发前冻结；改变目标/必需输入/专家方法产生新版本。
- **RouteRecord**：任务草案或版本标识、输入快照、候选目录及问题版本、原始 Jev 响应、程序检查、最终选择、模型配置、时间和用量。任务失败前产生的决策也保存；发布时引用准确记录。
- **ContextSnapshot**：消息截止点、必需与可选信息、资源/结果版本、作用域版本、假设/未知项。快照固定内容，当前权限决定能否读取和发布。
- **TaskReceipt / CheckRecord**：任务单和运行对应关系、结果引用、逐项检查依据、缺失/冲突、失败归因；专家自检与程序/校验专家结论分开。
- **ReturnRecord**：来源分支与结果版本、选定结论、必要前提/证据、目标分支修订、供讨论或已采用状态。首版选择完整结论块，不做任意文字剪切后自动保证语义完整。

已有结果正文继续保持单一来源，不为任务、节点、回执复制多份可变正文。方法内容与任务事实分开；方法版本首版仅固定配置和内容摘要，完整编辑发布界面留到 Stage 8。

### 2.2 三类状态与提交规则

| 状态层 | 最小表达 | 作用 |
|---|---|---|
| 执行 | 排队、运行、结束、失败、取消、中断 | 说明计算发生了什么 |
| 交付检查 | 待检查、通过、部分、返工、拒绝 | 决定哪些内容能交给下游 |
| 用户决定 | 供讨论、已采用 | 不由运行成功自动推导 |

保存另行显示保存中、保存失败/待确认、已保存。运行结束不等于交付通过；只有结果、回执、当前检查结论、依赖及对应业务指针原子提交成功才解锁下游。异步复核生成新检查记录，并原子更新交接资格，不重写原结果。

提交核对 command/run 身份、任务单版本、分支修订和当前权限。重复请求只返回同一结果；同 ID 改内容拒绝；保存重试不重新调用模型。回传及采用关系独立原子提交。取消依赖和旧成功结果不能代替本次失败的必需输入。

## 3. 技术选型：沿用什么、增加什么、暂缓什么

以下版本是项目当前锁定值，不代表外部最新版本；是否升级由兼容性和实际缺口决定，不因整理文档顺便升级依赖。

| 能力 | 当前选择 | 理由与边界 |
|---|---|---|
| 运行语言与环境 | Python ≥3.12、uv 锁定依赖 | 复用现有后端与评测脚本 |
| Agent 执行 | `openai-agents==0.22.2` + 当前 Core/ExecutePort | 已有工具、结构化输出与执行验收；不换 LangGraph/Deep Agents 等第二套引擎 |
| 模型接入 | 优先现有 SDK Model 注入和适配器 | 将实际配置绑定到每次运行，避免可变全局模型污染并发任务；现有 `engine.model` 优先级须调整或明确限制 |
| Jev 调用 | 一个类型化决策适配器，优先官方 API；现有 httpx 为首选传输候选 | 核对官方 SDK 的能力后选最简接法，不重写通用 HTTP 客户端；只实现当前 Choice 契约 |
| 多提供商 | 先复用 Agents SDK 已有模型接口 | 确有协议缺口时评估其 LiteLLM 适配；不先部署独立代理。每模型显式配置协议，无自动协议 fallback |
| 数据库 | SQLAlchemy 2.0.43 + psycopg 3.2.10 + PostgreSQL | 延续原子性和真实进程验收；不加第二个状态真源 |
| 资料 | 现有 Docling 2.129.0、PDF/OCR 组件、文件存储 | 复用已经验证的格式；复杂财报表格另测，不把 OCR 成功当财务字段正确 |
| API/界面 | Starlette/Uvicorn；React 19.2、Vite 7.3.6、React Flow 12.11.1 | 在现有页面上增加聊天与分支交互；研究树降为导航，保留 Markdown 渲染能力 |
| 测试 | pytest、真实 PostgreSQL、故障注入、Playwright/实际浏览器 | 控制、持久化、UI 和模型语义分别验收；浏览器不可用时明确替代证据与限制 |
| 证据 | 自有引用/支持关系服务，参考 PaperQA | 不为引用功能引入第二套资料库或 PaperQA 全部 Agent 流程 |
| 恢复 | Stage 6 首选评估 DBOS 外层适配 | 步骤级恢复，业务提交仍走现有接口；不把 DBOS 装饰器散进领域对象 |
| 评测与观测 | 先复用本地 evals、运行记录及 PostgreSQL | Langfuse 仅在需要标注/追踪工作台时评估，不作为结果数据库或研究可用性依赖 |
| 记忆与进化 | 暂不新增平台依赖 | Stage 7/8 建立评价与版本后，再按真实缺口评估记忆检索和候选生成工具 |

源码依据：[Python 依赖](../pyproject.toml)、[前端依赖](../frontend/package.json)、[模型适配器](../src/agent_core/adapters/openai.py)。外部接口参考：[Agents SDK 模型接口](https://openai.github.io/openai-agents-python/models/)、[TypeSafe Jev](https://docs.typesafe.ai/introduction)、[DBOS Python](https://docs.dbos.dev/python/programming-guide)、[PaperQA](https://github.com/Future-House/paper-qa)。在线文档可能对应不同版本，实施时核对锁定版本的类型和源码。

## 4. 开发顺序总览

历史 Stage 0–4 保留，不重新编号或宣布作废。在进入 Stage 5 前增加 R1–R3 三个补齐里程碑，分别补到已有持久化、调度和分支基础上。它们是当前开发阶段，不是另一套产品架构。

| 顺序 | 阶段 | 用户可看到的新增结果 | 依赖 |
|---|---|---|---|
| 已有 | Stage 0–4 | 独立执行、持久记录、并发、资料隔离、研究节点与版本 | 历史验收，开工前检查受影响基线 |
| 1 | R1 任务单与检查交接 | 专家任务可查看输入、交付要求、回执与失败原因 | 0–4 |
| 2 | R2 Jev 两步路由 | 同一任务按要求选择专家和模型，可查选择记录 | R1 |
| 3 | R3 聊天与分支融合 | 从消息分支、独立续聊、并发专家、选定结论带回 | R2 |
| 4 | Stage 5 证据与研究资料闭环 | 上传/联网资料形成可定位证据，报告可点击原文 | R3、既有资料服务 |
| 5 | Stage 6 持久执行 | 中断后保留已提交步骤并恢复剩余工作 | 5 |
| 6 | Stage 7 反馈和评测 | 对专家、路由、检查器归因并比较版本 | 5；本路线在6后实施 |
| 7 | Stage 8 方法与流程版本 | 可查看、发布、回退专家方法与研究模板 | 7 |
| 8（可选） | Stage 9 偏好与记忆 | 可确认、纠正、删除的偏好和获准经验 | 7/8，不是10的前置条件 |
| 9 | Stage 10 专家进化 | 生成改进候选，经留出评测与端到端检查后发布 | 7/8及必要回归 |

R3 完成代表“分支＋专家并发＋任务级路由”首个融合里程碑；Stage 5 完成才覆盖“带原文引用的公司比较”完整承诺。恢复和进化按后续阶段增加，不阻塞前面的可用产品。

## 5. R1 — 专家任务单、回执与交接检查

**最小链路：** 用户明确指定一个提取任务 → 主助手形成任务单 → 获准资料装配 → 指定专家执行 → 检查回执并保存 → 合格结果交给分析任务。此阶段使用明确指定专家和模型，Jev 在 R2 加入。

**复用与修改：** 复用 Ledger、应用事务、ScopeService、ContextBuilder、Dispatcher；参考 multi-agent-flow 的契约结构。增加 tasks 模块，扩展研究应用装配及结果视图；不改写 Core 工具循环。任务单由系统生成，默认折叠，不要求用户填表。

**必须交付：** 任务/运行分离、必需/可选输入、编号验收项、程序与语义检查分开、部分交付依赖规则、原子保存、独立任务上下文。搜索/提取/分析/综合方法用固定配置版本定义，首版不建完整方法编辑器。

**验收：** 缺必需资料不派发；缺单位返回部分交付且不能进入数值计算；取消依赖不算成功；同专家不同任务唯一标记互不串入；模型自报成功不能解锁检查；提交失败不解锁下游；保存重试不增模型调用；旧任务单的迟到运行不能覆盖新版。用真实 PostgreSQL 和新进程查询验证完整回执，并执行受影响 C0–C4 回归。

**实际体验：** 用户只提出“提取公司 A 现金流”，展开专家活动即可看到本次要求、缺失和返工原因。真实模型交付须人工核对来源/单位；脚本通过仅证明控制契约。

## 6. R2 — Jev 专家选择与模型路由

**最小链路：** 任务摘要 → 专家候选预筛选 → Jev Choice → 所选专家适用模型预筛选 → Jev Choice → 冻结配置 → 原 Dispatcher/ExecutePort 执行 → 回执验证。两个选择存在依赖，不并行让 Jev 独立猜两个可能不兼容的答案。

**复用与修改：** 增加 routing 模块和单一 Jev adapter；现有 SDK 优先提供多模型执行。任务级配置必须不可变，避免多个并发任务修改共享 Engine 的模型。专家身份固定已发布方法版本，Jev 不任意挑历史方法。旧演示 router 的固定三专家策略不承担生产自动选择；替换过时路径，不增加双协议兼容层。

**必须交付：** 合格候选目录、用户指定优先、唯一候选免调用、无法匹配选项、问题与目录版本、原始决策与程序排除记录、路由对外处理范围、任务内保持、受控升级与全链路用量。模型描述来自受控目录和实测，不让材料中的指令修改能力声明。

**验收：** 空候选/低确定性/API失败不启动未核验模型；指定专家不被替换；“继续”不降档；模型不支持工具或容量不足被排除；装配后超容量重新检查；两任务确实使用各自配置；重选不重置预算；Jev 摘要不含未授权唯一标记。

**真实验证：** 至少两位可竞争专家、两种合格执行模型及真实 Jev 请求，证明两步选择实际影响执行；同时测固定模型和规则选择对照。先冻结样本与门槛再跑，记录质量、总费用、延迟及路由阻断率。不因 API 返回结构正确宣布路由有效，也不在文档中预承诺节省比例。

## 7. R3 — 统一聊天、消息分支与选择性回流

**最小链路：** 主线对话得到结果1 → 从指定消息分出方向2/3 → 各分支独立续聊并调用专家 → 用户选定结论块带回主线 → 明确采用或继续讨论。

**复用与修改：** 扩展现有研究节点为持久探索空间，关联有序消息和分叉截止点；复用结果挂载、版本、命令幂等和 revision 检查。聊天为主界面，React Flow 保留导航；只维护一套节点/分支身份，不并行维护互相同步的两棵树。

**必须交付：** 当前分支显式显示；选专家与切分支分开；后台任务折叠且不自动成为树节点；从消息或结果分叉；选定结论块、依据和限制回传；供讨论/采用分别记录；主线后续消息不自动注入旧分支。

**验收：** 消息截止点之后的唯一标记不进入新分支；兄弟分支隔离；一个分支可调用多个专家；同专家跨分支不串上下文；回传不能遗漏必要前提；撤权阻断历史访问和迟到发布；过时目标修订拒绝回传；上游更新只提示。真实浏览器完成两场景、停止/保存失败/续研操作；R1/R2 与原0–4受影响回归通过。

**范围边界：** 首版选完整结论块；不做 Git 式文本自动合并、冲突自动解决或跨分支持续同步。引用可先显示来源定位，完整证据支持在 Stage 5 验收。

## 8. Stage 5 — 资料、证据与最终研究产物

**最小链路：** 上传报告＋范围内联网发现 → 抓取固定来源快照 → 解析并核对字段 → 专家生成结论与证据关系 → 公司比较表/报告 → 点击结论返回原文。该阶段分两个连续小增量：先完成已有资料的证据闭环，再接通一个真实搜索提供方；前一个增量随时可运行，但两个都通过才宣告本阶段完成。

**复用与选型：** 继续用 ResourceService/Docling/OCR；参考 PaperQA 文档身份、片段和引用组织，证据服务复用已登记来源。搜索通过单一 SearchProvider 接口接入一个可用提供方，开工时按凭据、中文相关性、可追溯 URL 和调用契约选择并锁定；不提前接多家。普通获准搜索自动接入，不逐条让用户确认。

**必须交付：** discovery 与已读取正文分开；主体/报告期/币种/单位/口径由提取专家提议、程序和校验步骤核实，未知显式保留；解析失败、扫描件和重复资源沿用现有生命周期；引用固定 source/parse/页或表格定位；区分有引用与引用确实支持结论；支持反证与缺证。

**验收：** 通用财报样本而非仅结构化夹具；中文扫描件、混合表格、重复文件、搜索摘要冒充证据、失效来源、期间不一致、错误单位、引用存在但不支持结论；所有引用重验当前权限。报告回传后仍可定位准确旧版本。外部搜索不可用显示待验收，不用批准 URL 目录冒充通过。

**产物：** 三家公司同期间现金流与竞争风险比较；选择一家续研；最后报告和比较表可逐项查看来源与限制。头脑风暴方案仍允许假设，外部事实单独核实。

## 9. Stage 6 — 持久执行与中断恢复

**最小链路：** 已完成一个专家任务 → 杀死 worker → 重启 → 查询已提交产物 → 仅恢复剩余步骤 → 检查后汇总。

**选型与边界：** 评估并固定 DBOS 版本，在外层包装任务步骤，继续调用业务幂等命令；不替换 Core、ScopeService 或业务提交。固定任务单、路由、方法、模型、输入版本；恢复前后重新检查当前权限。明确步骤级恢复，不承诺 token 级恢复或跨外部 API 的恰好一次。

**验收：** 外部调用前、调用后未提交、提交后三处真实进程崩溃；重复投递、撤权、取消、旧代码检查点拒绝；完成步骤不重算，可能重做的未提交 API 请求有记录并计预算。统一外层/SDK 重试计数，避免次数相乘。直接执行与持久执行产出等价业务状态；前序端到端回归通过。

## 10. Stage 7 — 反馈、评测与路由证据

**最小链路：** 用户指出某个结果单位错误 → 绑定任务/运行/方法/模型 → 核验归因 → 冻结案例 → 比较改进前后质量和总成本。

**选型与边界：** 从现有 evals 和数据库开始；只有需要协作标注/可视化追踪时再评估 Langfuse exporter。日志导出失败不影响研究提交。错误回答不自动变为标准答案，用户偏好与事实错误分开。

**验收：** 反馈绑定正确版本、幂等、来源权限、开发/留出集分离、检查器误判、无标签数据不冒充已验证。分别测专家选择、模型选择、交接完整性与最终交付。历史路由实验比较固定模型、规则、Jev、仅历史证据、Jev＋历史证据，控制任务拆分和候选池。历史证据无额外收益时不接入在线路径。

## 11. Stage 8 — 专家方法与流程版本

**最小链路：** 将经验证的专家指令/示例和研究流程保存成版本 → 用新资料实例化 → 固定版本执行 → 切换版本只影响未来任务。

**实现：** 扩展 R1 的只读方法配置为版本资产和 active 指针，增加受限参数化流程编译；输出原有任务/依赖计划，不建通用 DSL 或第二套运行器。专家方法、模型路由策略和业务研究流程分开版本化。

**验收：** 缺参数不运行；模板不带入原公司数据；权限只取交集；依赖无环；在途任务不受发布影响；回退后新任务使用旧方法；人工流程与等价模板流程保持业务一致。旧版本保留为历史资产，不代表增加旧接口兼容或迁移代码。

## 12. Stage 9 — 可选偏好与获准记忆

**最小链路：** 用户保存“公司研究先看现金流” → 新任务显式应用 → 本次指令覆盖旧偏好 → 删除后不再召回。

**实现与验收：** 先复用 PostgreSQL 和 ContextBuilder 贡献接口。需要更复杂召回时再评估旧规划中的 Mem0/Letta 等，不能因为有参考项目就全部接入。检查来源、确认/过期状态、跨范围泄漏、撤权与删除；记忆不能隐藏反证或变成不需来源的事实。停用后基础研究继续成立。Stage 10 不依赖此阶段完成。

## 13. Stage 10 — 专家独立进化

**最小链路：** 经核验反馈 → 产生某位专家的方法候选 → 固定数据比较 → 留出测试 → 跨专家端到端测试 → 用户确认发布 → 可回退。

**实现与边界：** 候选首先限于指令、示例、查询/校验顺序和受限流程参数；不改 Core、工具实现、权限、验收阈值或任意生产代码。候选不自动生效，不等同模型权重训练。生成器复用现有模型执行；先参考旧规划中的候选隔离/发布模式，不部署完整自主训练系统。

**验收：** 候选不污染 active；无完整证据不能发布；留出集不进入候选提示；发布 compare-and-swap；在途旧版本不变；局部改进不能破坏上下游契约；质量、范围与成本硬门槛通过后再考虑偏好收益。至少演示一个单位核验方法的改进与一次回退，并保留失败候选。

## 14. 起始执行策略与停止行为

下表是本路线采用的开发起点，须在相应阶段开工时记录成固定配置；属于可检验的默认方案，不是已经实测最优参数。正式质量/confidence 门槛需用开发样本确定，再冻结用于留出测试。

| 项目 | 起始规则 |
|---|---|
| 并发 | 同时最多3个专家运行，继承既有调度默认；同一任务串行，独立任务可并行 |
| 委派深度 | 一层专家；专家通过缺口回执请求协调者补派，不自行递归 |
| 完成策略 | 独立任务 all_settled；失败阻断其必需下游，不取消无关兄弟 |
| 计划预算 | 接受计划时固定任务数N；专家总启动上限2N，每任务最多2次尝试（含升级/返工），共享预算；新计划不能隐藏旧任务累计消耗 |
| 重选 | 初始选择之外，每任务最多一次模型重选；改变专家/方法需新版任务单，并沿用原任务预算 |
| Jev 调用 | 一个决策点超时10秒；暂时性网络错误最多额外重试1次；格式/权限错误不盲重试。唯一候选和用户指定免选择调用 |
| 任务时限 | 沿用既有单运行限制；派发组起始120秒，超时保留已提交项并停止新增；长研究由固定有限步骤构成 |
| 部分结果 | 默认不满足必需依赖；仅任务单预先允许时使用，并携带缺失/限制 |
| 停止 | 用户停止、权限变化、超限时停止新增并取消受影响在途运行；迟到结果不发布 |
| 费用 | 固定目录价格和调用限额，记录实际/估计/未知；金额上限必须在真实评测试跑前指定，不填虚构默认金额 |

金额与 token 观测阈值不冒充绝对账单封顶。并发请求、未知用量和外部计费存在差异；若提供方不能保证上限，则显示为估算及停止策略。正式自动执行启用前，要冻结可接受质量、路由阻断率和总成本门槛，缺项时可完成离线开发但不得宣告自动路由验收通过。

## 15. 每阶段的交付、测试与差距闭环

每阶段都执行：**调查可靠复用 → 最小链路跑通 → 对照产品设计 → 定位 gap → 最小修改 → 本阶段及前序连通回归 → 真实语义/交互验收。** 不先搭一批未来空模块，也不以测试数量代替需求覆盖。

| 交付物 | 必须包含 |
|---|---|
| 启动与复现说明 | 可运行入口、锁定版本、必要外部条件、数据与文件备份范围 |
| 复用记录 | 参考固定提交、采用模块、许可、API契约、未采用部分 |
| 符合性矩阵 | 需求ID/产品章节 → 实现文件与接口 → 测试/交互证据 → 通过或gap |
| gap记录 | 失败现象、原因、补齐内容、修复后验证；保留失败证据 |
| 控制与持久化证据 | 命令、退出码、原始输出、真实PG及新进程查询、模型调用计数 |
| 真实语义与UI证据 | 固定资料、实际模型配置、结果和人工复核；脚本替身明确标注 |
| 当前状态 | 已完成 / 待修复 / 待外部验收；缺凭据、数据库或浏览器不标通过 |

回归覆盖当前改动涉及的前序契约和完整研究链路，阶段结束运行必要累积套件。故障重点包括保存失败、提交响应丢失、重复命令、取消、撤权、迟到执行、模型/路由失败；持久恢复阶段增加真实崩溃与重启。

不保留过时接口、迁移脚本或兼容层。若当前开发数据契约确需变化，使用新专用验收库和新的当前入口；旧库、文件与历史验收证据保留，不自动删除用户数据。保留历史成果与方法版本是产品需求，不是运行旧协议。

## 16. 开工前仍需冻结的具体项

1. R1：四类专家的初始方法与交付契约，先用一个提取→分析任务验证。
2. R2：真实可用 Jev 接口和固定版本、至少两种执行模型、能力目录、价格来源、预算与测试集门槛。缺凭据先完成离线契约，真实验收保持待完成。
3. R3：消息快照采用“必要正文＋固定引用按需读取”；首版完整结论块回传。用长对话验证容量和用户理解，再决定摘要策略调整。
4. Stage 5：一个真实搜索提供方与一组获准通用财报样本；文档未冻结品牌，不能将该选择遗漏到验收之后。
5. Stage 6：DBOS 锁定版本、worker部署和任务版本策略；此前继续当前个人本机单执行进程边界，不提前承诺多用户或云部署。

下一步从 **R1 任务单与检查交接** 开始。R1 通过后接 R2，再以 R3 验收用户最关心的统一聊天、专家并发与分支回流闭环。
