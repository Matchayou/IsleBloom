# 同一 Agent 底座的三个业务方向

更新：2026-10-18。当前选择：商品选品推荐、智能创作、游戏制作。本文是方案，不表示改造已经实现。

## 一、定位与范围

同一个可持久执行、带分层记忆和专家交接的 Agent 工作台，分别完成商业决策、内容生产与可运行软件交付。

当前范围：选品面向消费者；智能创作先做品牌图文与短视频脚本；游戏制作先做单个引擎的 2D 小游戏。它们是便于落地的设计假设，仍可按用户实际意图调整。选品围绕用户需求、预算、使用环境、购买与使用反馈，输出购买建议。

| 方向 | 主要业务对象 | 最小交付 | 记忆重点 | 检索重点 | 协作重点 |
| --- | --- | --- | --- | --- | --- |
| 商品选品推荐 | 用户、购买任务、商品型号、商家报价 | 个性化候选、取舍与证据 | 用户偏好、已有设备、使用反馈 | 需求约束、兼容性、规格与当前报价 | 澄清需求、调查候选、独立校验 |
| 智能创作 | 品牌、栏目、创作 brief、内容版本 | 可编辑图文包或分镜脚本 | 品牌风格、明确偏好、跨作品一致性 | 参考案例、素材、品牌规范 | 创意分支、选定方案、定向修改 |
| 游戏制作 | 游戏项目、场景、资源、代码版本、构建 | 可运行、可试玩的小游戏 | 已确认设计决策、项目约定 | 代码/场景依赖、引擎版本、运行错误 | 依赖交付、受控集成、测试返修 |

三个应用先各自内聚，实现第二次真实复用时再提取共用部分。不先建设通用行业配置平台，不增加另一套编排框架。

## 二、当前底座与改造边界

静态阅读确认：已有 user/project/specialist 记忆、偏好与经验、确认/草稿、版本和过期；已有 ContextPacket、专家消息、任务依赖与独立复核；已有受控工具、动态工具启用、账本、DBOS、Git worktree 编码工具和运行分析。

当前资料/历史检索包含 SQLite FTS5 BM25，单来源片段搜索采用词项匹配；记忆选择使用独立轻量 LLM。不能描述为已实现完整的向量/多模态/图检索。未在 src 和依赖声明中发现 MCP 接入实现。

现有记忆主要表示偏好和经验。以下内容需要明确分开：

- 长期记忆：用户/品牌/项目偏好、经验证经验，带来源与适用范围。
- 业务记录：SKU 价格库存、品牌规范版本、游戏设计决策、场景与资产清单。
- 执行上下文：当前候选、被否决方案、任务依赖、模型与工具结果、产物引用。

业务记录可以被检索进入上下文，但不应全部写进 MemoryEntry。当前产品为单机工作台，业务对象隔离不能冒充完整多租户能力。

## 三、商品选品推荐：消费者购物决策助手

用户已明确：帮助消费者选择适合自己的商品，不面向商家的采购选品。重点建设跨会话个性化、反馈驱动的数据飞轮和公开 benchmark 评测。

详细方案、数据流和 benchmark 取舍见 [消费者选品与数据飞轮](consumer-shopping-agent.md)。

## 四、智能创作：具有品牌记忆的内容工作室

### 1. 首版业务闭环

输入：“为这个收纳品牌做一套小红书图文，面向租房人群，语气自然，突出真实使用场景。”

输出：两个创意方向，用户选定后交付标题、正文、封面、配图说明及可编辑内容包。短视频先交付分镜和脚本；图片生成稳定后再加配音、剪辑和视频渲染，逐层形成可交付产品。

### 2. 记忆怎么改

- 品牌规范：Logo、颜色、字体、语气、禁用表达、产品事实，使用版本化品牌资料。
- 长期偏好：用户确认的表达习惯、偏好结构、对已采用作品的明确评价。
- 栏目状态：目标受众、固定结构、已发布主题和选题覆盖，放业务记录。
- 角色/世界观：若转向故事创作，增加角色卡、设定与事件时间线；事实变化有版本，不用一段滚动摘要代替全部设定。
- 用户说“这一篇活泼一点”仅影响本篇；“以后这个品牌都不要用夸张标题”才进入长期规则。
- 点赞量和完播率是外部观测数据，不能单靠模型猜测形成“爆款经验”。

### 3. 身份与交流怎么改

创意负责人提出方向 → 用户选择 → 文案和视觉专家在同一 brief 下协作 → 编辑复核品牌一致性与需求覆盖 → 定向返修。

首版可先用创作者和编辑两个角色，把文案与视觉作为创作者的两类工具任务；复杂度增加后再拆独立视觉专家。多版本方案用现有分支表达，避免所有草稿混在一条历史里。

交接包建议：`brief_version / audience / selected_concept_id / brand_refs / copy_version / asset_refs / change_request / acceptance_criteria`。

返修意见指向具体产物和位置，例如“封面标题保留，第二段改短”；不要每次整套重做。未被采用的分支不能覆盖正式品牌规范。

### 4. 工具怎么接

首版接一个图像生成能力和本地内容包导出；通过现有受控工具封装提供商 API。后续择一接入 Canva 或 Figma 的可用连接器/MCP，最后再考虑音频、视频工具，不同时接所有平台。

长耗时生成记录 job_id、状态和结果引用；超时后先查询原任务，避免重复扣费。保持可编辑源文件、预览和版本关系。内容发布属于单独动作，首版完成交付即可。

### 5. 检索怎么改

当前 brief → 必需品牌规范 → 同栏目已采用案例 → 相似受众/结构的参考内容 → 可用视觉素材。

品牌规范必须注入，不能因语义得分低被丢掉。文本检索重视结构、语气、受众；素材检索按用途、尺寸、色调及来源过滤，后续再增加图文语义检索。引用作品是学习可描述的表达规律，生成内容不应照搬原文。

引用关系从文章级推进到段落/镜头/素材级；产品参数仍需来源，不得为创作效果编造卖点。

### 6. Demo 与评测

创建两个风格明显不同的品牌。展示同一产品在两个品牌下的不同产物，以及连续创作后仍遵守品牌规范。用户指定只改第二段和封面时，检查其他内容保持原版本。

评测：brief 约束满足率、品牌一致性、产品事实正确率、人工盲评偏好、修改定位准确率、无关改动率、跨品牌信息泄漏、每个被采用产物成本。不能只用另一个 LLM 的主观评分证明质量。

产品参考：Canva 的 Brand Kit/Brand Voice 将品牌资产和语气显式管理；Adobe Firefly Boards 用参考板、方向探索和分镜支持创意迭代。可借鉴“品牌规范 + 分支探索 + 选定后制作”的流程。

- https://www.canva.com/help/brand-voice/
- https://www.canva.com/help/find-and-manage-brand-assets/
- https://www.adobe.com/products/firefly/features/boards.html

## 五、游戏制作：交付可试玩原型的开发工作室

### 1. 首版业务闭环

输入：“做一个 2D 俯视角收集小游戏，玩家移动、收集三件物品、避开敌人，支持胜负和重开。”

输出：可打开的工程、可运行构建、玩法说明、测试与已知问题。建议首版只选 Godot 4 做 2D；这是控制范围的建议，不表示已经核验本机引擎或 MCP 能力。用户已有指定引擎时沿用该引擎，不同时支持多种。

### 2. 记忆怎么改

- 用户长期偏好：画面、操作方式、节奏等明确偏好。
- 项目规范：引擎版本、输入映射、分辨率、资源规格、代码与目录约定。
- 设计决策：核心循环、胜负条件、明确取舍及依据，做版本化设计记录。
- 当前工程状态：节点树、信号、资源路径、脚本引用、构建结果，从工程实际读取，不凭旧记忆判断。
- 调试经验：附错误、修复、验证结果、适用引擎版本；未经验证的猜测只留在任务轨迹。

游戏制作 Agent 与游戏内部 NPC Agent 是两条产品线；首版只做前者，避免把开发工作室和运行时智能混在一起。

### 3. 身份与交流怎么改

制作人限定范围与验收 → 实现者完成灰盒玩法 → 测试者验证胜负闭环 → 视觉/关卡任务按固定接口增量加入 → 集成与复验。

首版先使用制作人、开发者、测试者三种职责；美术生成先作为工具任务。素材和独立关卡可以并行，主场景与共享脚本由单一责任者集成。策划描述、资源规格和代码接口必须在交接时一致。

交接包建议：`design_version / base_commit / scene_path / allowed_files / input_actions / asset_manifest / acceptance_checks / build_ref`。

资源变化只重跑受影响的集成与验收，但必须先有明确依赖。没有依赖记录时不宣称已经实现智能增量构建。

### 4. 工具怎么接

复用现有 Git worktree、受控读写与固定测试 profile。核验目标 Godot MCP 的实际工具后，只开放需要的场景检查、运行、日志和截图能力；生成资产接一个图像工具即可。

执行边界清晰：文件修改走项目受控工具；引擎操作走允许的 MCP 动作；修改后测试失效，重新验证当前内容。worktree 是工作区隔离，不是 OS 沙箱。

### 5. 检索怎么改

任务涉及玩法 → 查找场景与脚本 → 沿节点引用、信号和资源依赖扩展 → 查询匹配引擎版本的官方文档 → 结合运行日志定位。

先使用实际目录、符号与场景资源解析，不为小项目预先部署图数据库。需要语义召回时增加代码/文档索引；运行错误和当前工程始终优先于历史类似项目。

游戏资源检索需理解尺寸、动画帧、碰撞范围、命名和导入配置。看起来像正确素材不代表可以直接接入工程。

### 6. Demo 与评测

先完成灰盒移动→收集→受伤/失败→胜利→重开，再替换视觉。用户追加“收集后增加倒计时”时，只修改相关逻辑并复验已有玩法。另演示一次缺资源或信号连接错误的定位与修复。

评测：工程导入/启动成功率、必需玩法通过率、胜负与重开状态正确率、缺失资源数、运行错误、修改后回归率、达到可试玩状态的时间与成本。能启动不等于可玩；趣味性需独立人类试玩评价。

产品参考：Unity 的项目内 AI 工具强调引擎上下文、编辑器工作流与资产生成。可借鉴“理解当前工程并操作编辑器”的模式，具体 Godot 实现仍须单独核验。

- https://docs.unity.com/en-us/ai
- https://learn.unity.com/collection/build-with-unity-ai

## 六、三个独立应用，也可以形成一条展示链路

各应用先能独立交付，再考虑共享案例：

“用户为自己的桌面选择收纳商品 → 制作个人使用分享内容 → 制作同主题互动小游戏。”

选品向创作只交接已确认商品事实、目标受众和卖点证据；创作向游戏交接选定视觉方向及可用素材。推荐结论不自动变成事实，创作生成的卖点不回写商品数据库。

这个链路适合展示复用，但互动营销小游戏只是可选业务案例，不应限制游戏制作应用只能做营销。

## 七、落地架构与顺序

### 共用层

继续复用身份、任务、交接、预算、受控执行、版本化结果、记忆审查、授权、恢复和运行分析。业务规则、对象模型、检索入口和验收产物分别放入三个业务模块。

MCP 采用薄适配，先检查已装 SDK 的能力与类型。所有工具调用仍经过既有 Broker；工具自报只读/幂等不能代替本地授权。外部任务记录稳定动作 ID 与回执；未知完成状态先查证，不自动重发。

### 代码落点

| 现有模块 | 改造职责 |
| --- | --- |
| memories/ | 继续处理偏好和经验证经验；补充真实需要的业务适用范围 |
| context/selection.py、retrieval.py | 业务对象过滤、来源选择和业务检索；保持证据版本 |
| collaboration/、agent_identity.py | 角色职责、产物协议、任务依赖和交接条件 |
| adapters/、controlled/ | MCP/提供商接入与受控执行，不另建调度器 |
| coding/ | 复用游戏工程受控读写与测试能力 |
| 新增业务目录 | 选品对象与计算、创作 brief 与内容版本、游戏设计与验收 |
| frontend/src/workspace/ | 展示商品比较、内容版本预览、游戏运行与测试结果 |
| evals/ | 三类独立案例集，复用账本中的成本、时延和工具统计 |

不直接把现有研究类型全部改名后套到新业务上。先让一个应用从真实入口到结果可运行，再提取经验证可共用的部分；需要替换的旧路径直接移除，不保留新旧双轨兼容逻辑。

### 推荐顺序

按当前项目改造距离：选品 → 图文创作 → 2D 游戏。选品更接近已有研究与证据流程；创作增加多模态产物和定向修改；游戏增加工程状态与实际运行验证。若目标岗位明确偏 Coding Agent，可把游戏提前。

每个方向先完成一个端到端任务，再加业务记忆，再接一个必要外部工具，再验证专家协作是否有收益。每层都保留可运行产品。

对照：同一数据和模型条件下，依次比较基础单 Agent、业务检索、业务记忆、多 Agent。记录质量、延迟和实际消耗；保留独立留出案例，避免只在演示样例上调优。初始 20–30 个案例用于发现问题，不构成生产可靠性结论。

面试讲述重点分别是：选品的个性化购买决策，创作的长期一致性与定向修改，游戏的依赖协作和可运行验收。所有尚未实现的能力只作为设计说明，不写成已完成经历或虚构收益。
