# 消费者选品 Agent：个性化、数据飞轮与评测

2026-10-18。讨论设计，尚未实施或跑分。本文替代先前商家选品假设。

## 产品闭环

定位：持续理解用户约束、能核验商品证据并从反馈改进的购物决策助手。

以耳机为首个可选垂类：用户提出预算和场景→澄清关键缺口→结合已确认偏好与已有设备→搜索候选→核验规格、兼容性和报价→给出少量有不同取舍的候选→用户比较/排除/选定→可选收集使用反馈。选耳机是便于表达权衡的示例，不表示已经准备数据源。

目标是满足需求、减少决策成本、提高使用满意度；用户决定暂不购买也可以是正确结果。首版不需要真实下单权限。

## 四类上下文

| 内容 | 示例 | 管理方式 |
| --- | --- | --- |
| 持久偏好 | 明确表示不接受入耳式 | 用户确认、来源、适用类目、版本与撤销 |
| 用户事实 | 已有手机型号与连接设备 | 独立用户事实记录，附时间与来源；变更可纠正 |
| 当前购买任务 | 预算、通勤用途、给谁买 | 任务状态；为他人买不覆盖本人偏好 |
| 商品证据 | 型号、规格、报价、评价 | 商品/变体/商家报价分开，附来源和观测时间 |

现有偏好/经验记忆可以复用；不把设备清单与商品库强塞为偏好。当前任务明确要求优先于历史偏好，冲突时指出并确认。不能把某次预算概括为终身消费能力，点击单一商品也不能直接生成长期偏好。

## 角色、工具与检索

主助手维护需求与最终解释；商品调查专家搜候选和证据；独立校验专家检查硬约束、型号、兼容性、价格时效和缺口。简单任务走单 Agent，复杂比较才委派。

交接结构包括购买任务版本、约束、获准用户信息、商品/变体 ID、证据引用、报价时间、不确定项。共享证据，不广播用户全部历史。

检索顺序：当前需求和适用记忆→必要澄清→类目/属性过滤→语义与关键词候选召回→具体变体核验→规格/评测/评论证据→报价刷新→比较。主观评价与官方规格分开；无法核验的关键约束显示未知。

首个外部接口只需商品搜索/详情/报价，按可访问官方 API 或获准来源确定。MCP 是工具传输层，不会自动提供商品数据；其适配仍经过项目 Broker。先用固定商品快照打通任务与评测，再接实时数据。

## 两个反馈循环

### 用户个性化循环

记录真实曝光与排序、用户反馈、反馈对象和原因→形成偏好候选→显式确认或保留为弱信号→检索适用偏好→下次决策→检查用户是否仍认同。

“戴久了耳朵疼”先是某商品的使用反馈，不能立即推断用户拒绝所有同类产品。给家人购买、价格过高、已经买过、外观不喜欢，必须区分原因。

### 系统能力循环

记录失败轨迹→标注是需求、召回、事实、排序还是工具错误→人工审查标签→加入开发案例→修改一个明确组件→冻结留出集与公开测试回归→通过后发布→继续收集反馈。

本项目不训练模型。改进对象限定为检索、澄清策略、约束校验、记忆选择与多 Agent 编排。模型自我肯定不能直接充当监督标签。

最小事件字段：event_id、匿名化用户 ID、任务 ID、策略版本、商品/变体与报价快照、曝光位置、已展示证据、工具轨迹、反馈类型/原因/来源、发生时间。外部购买、退货和满意度只记录确实取得的反馈，未知不填负例。跨用户学习只使用获准且经处理的数据，个人记忆独立可删除。

点击是弱反馈，选择/购买也不等于满意。曝光顺序影响点击；首版记录位置和策略版本，对同等合格候选可做小范围随机对照，不在没有曝光概率与支持条件时声称完成无偏离线反事实评估。

## 公开 benchmark 的分工

以下仅核验官方论文、仓库与数据页，尚未下载环境、验证许可证细节或完成复现。论文发表不是环境可复现或业务有效的保证。

| Benchmark | 能测什么 | 局限与建议 |
| --- | --- | --- |
| ShoppingBench | 商品搜索、知识约束、多商品/商家、优惠券和预算下的端到端工具任务 | 主 Agent 任务候选。官方仓库提供数据与评测入口，但环境较重，web 部分涉及外部搜索；固定代码/数据并分开报告静态与联网结果 |
| WebShop | 根据指令搜索、浏览、选择属性并购买的模拟购物任务 | 经典基线，适合先接通评测；不直接证明跨会话个性化或真实使用满意度 |
| Shopping Reasoning Bench | 购物推荐、比较、问答和多轮导航的细粒度回答质量 | 有专家 rubric 和公开数据，适合决策解释；不是完整工具执行 benchmark，LLM judge 也需抽检 |
| LongMemEval | 信息提取、多会话、知识更新、时间与拒答 | 测记忆能力；不是购物 benchmark，不能用其 QA 分数证明商品推荐效果 |
| ShopperBench | persona 引导的个性化购物行为 | 有 EACL 2026 论文，适合作为补充；本次未从论文核验可直接复现的完整官方代码/数据入口，不列为首个必跑项 |
| τ 系列 retail | 用户交互、业务工具和政策下的客服执行 | 后续订单/退换业务再考虑，不能代替售前推荐；当前官方仓库已有更新，必须固定具体版本，不混用旧榜单 |

用户进一步指定关注 ShopSimulator、VitaBench、shopping-grpo-longhorizon，优先级据此调整：ShopSimulator 作为中文购物交互主评测；美团 VitaBench 2.0 作为跨任务个性化记忆评测；原版 VitaBench 作为跨场景工具能力补充；shopping-grpo-longhorizon 作为训练和审计流程参考。上表其他 benchmark 暂为补充候选。

### 用户指定项目的分工（2026-10-18 补充）

- ShopSimulator 官方环境支持单轮/多轮、普通/persona 组合，直接覆盖需求澄清、细粒度商品与规格选择。固定官方版本与协议后先复现单 Agent，再对比本项目编排。persona 注入不等于从历史学习用户偏好。
- 原版美团 VitaBench 主要是外卖、到店、出行等生活服务的交互与工具组合；不是纯商品选购 benchmark。2.0 增加按用户连续子任务积累记忆，并支持自定义 memory backend，适合接入现有记忆服务。不能把 groundtruth 偏好作为实际系统可用输入；只用于 oracle 对照。两版分开报告。
- shopping-grpo-longhorizon 暂按 YYHDBL 同名仓库理解。它是基于 ShopSimulator 的后训练工程，不是另一套独立官方 benchmark。仓库使用冻结 Environment v2.1、Reward v3 和 Final-200 Clean。自定义奖励、留出集与原版任务协议不可混用成绩；task_id 不重叠也不自动保证商品/任务模板无泄漏。
- 用户已明确不进行 SFT/GRPO。只参考该项目的环境适配、动作守卫、观察投影、轨迹记录及独立评估方式；模型权重保持固定。
- 所有对照固定模型与推理设置，只改变记忆、检索或编排。总 token、环境动作、专家调用与延迟均需报告。

## 保持评测有效

- 评测 adapter 只转换观察、动作与结果；不向模型暴露参考商品、rubric、奖励细则、隐藏用户画像或未来消息。
- 原版成绩保留原有动作空间、数据、分割和评估器。改成自定义 search API、增加用户历史或翻译中文，都应单列变体；不能称为原版可比成绩。
- 每个独立任务重置状态与记忆，除非官方协议明确要求跨任务学习。多 Agent 共享该题总预算，各模型调用与工具成本全部计入。
- 固定模型版本、代码与数据版本、用户模拟器、judge、工具和预算。真实网页检索与冻结商品快照单列。
- 将端到端任务成功、约束满足、证据正确、记忆 QA、时延和成本分别报告，不混成任意综合分。重复抽样，并按任务聚合计算区间。
- 测试集轨迹不回流开发/经验库。开发时复盘的题转开发集；另外锁住未查看的测试集。公开 benchmark 可能已被基础模型见过，因此还需未公开业务留出集。

## 业务补充评测：个性化飞轮是否有效

公开 benchmark 不足以证明长期购物满意度。另建跨会话测试，先存偏好/事实，再提出新任务，检查偏好纠正、临时例外、给他人买、兼容性与未知项。按用户/会话隔离并按时间切分，未来购买/退货不能进入过去推荐。

必须包含：旧偏好被纠正、用户明确忘记某信息、同一词在不同类目含义不同、当前预算与历史预算不同、无商品满足硬约束、低价但不兼容、型号/变体混淆、价格过期。

对照 A 基础单 Agent；B 加业务检索和约束；C 加用户记忆；D 加反馈后的检索/排序更新；E 加必要专家。分别估计每一项贡献，同一批数据和计算预算规则下比较。对学习效果，固定训练截止时间和测试集，比较更新前后策略；对用户价值，再做获准真实用户的盲评或小范围对照。

优先观察约束满足、有效候选召回、事实证据正确、偏好更新准确、重复提问、明确选择原因、用户确认有帮助、使用后满意度与成本。没有购买/使用结果时只声称改善代理指标。
