## 1. 产品定位与核心动机

面向个人研究者的多专家协同助手。用户通过统一对话入口提出问题、探索新想法；主智能体协调具有独立任务上下文和明确专长的专家，按任务选择合适模型，组织并发研究，汇总有依据的结果。用户可从对话或专家结果创建探索分支，保留共同背景，独立推进，并将选定结论带回主线。

多专家设计的根本原因是：让能力围绕专精任务积累，每个专家可以独立评测和改进，同时避免不相关的过程与信息混入同一个上下文。分支承载用户的思路变化，模型路由控制每次执行的能力与成本。

确定方向：

- 面向个人研究者；输入包括自然语言想法、用户上传资料和联网搜索资料。
- 多专家协作与分支探索融合在同一产品闭环，首个融合里程碑必须同时验证两者。
- 用户不需要逐个配置或管理大量智能体，可以主要与主助手对话。
- 用户可以明确指定某个专家接收任务；未指定时，由主助手判断自行处理或分派。
- 每个专家围绕明确任务专精，拥有独立任务上下文和各自的方法改进路径。
- 按任务与路由选择不同模型；专家身份不绑定单一模型。
- 专家选择与模型选择由 Jev 负责；主助手负责理解目标、拆解任务、组织交接与汇总，系统负责强制执行权限和预算。
- 公司研究以比较表和报告为最终产物；通用探索也可以产出方案、假设、决策依据和待解问题。研究树是过程记录，不要求用户先画树再研究。

## 2. 用户问题、预期收益与验证边界

| 用户问题 | 产品能力 | 预期收益 |
|---|---|---|
| 一个会话承担所有工作，历史越来越杂 | 专家任务上下文隔离、明确结果回传 | 减少无关信息干扰，便于定位错误 |
| 全程使用同一种模型，能力或成本难以兼顾 | 按任务类型、难度、错误代价与预算路由 | 在可接受质量下控制总成本 |
| 聊天中出现新想法，重新开聊需要重复背景 | 从指定消息或结果创建分支 | 新方向继承共同背景并独立发展 |
| 多 Agent 导致窗口和管理负担增加 | 统一入口、专家活动折叠、主助手汇总 | 用户管理目标与想法，系统管理执行 |
| 同类任务反复犯错，经验难以复用 | 按专家归因反馈、冻结评测、版本化发布 | 对某一能力持续改进且可追溯回退 |
| 分支结论被用于主线后，来源与变化难追踪 | 选定结论回传、结果版本与依赖记录 | 明确采用依据，发现上游变化 |

这些收益是产品假设。多专家与经济模型不保证天然更准或更便宜；规划、上下文传递、重试、升级和汇总都产生开销。评价以实际成功率、质量、耗时与总成本为准。相同模型更换角色提示也不自动产生独立可靠的专家判断。

## 3. 核心对象与关系

| 对象 | 定义与生命周期 | 例子 |
|---|---|---|
| 研究项目 | 一组相关目标、资料、主线与分支的组织单位 | 三家公司比较 |
| 主线 | 当前主要讨论路径，由主助手协调 | 判断应深入研究哪家公司 |
| 探索分支 | 长期保存的目标、对话、挂载与结果集合 | 单独研究公司 A 的海外业务 |
| 专家定义 | 可复用的职责、工具、输出契约、方法版本、评测依据与模型策略 | 财报数据提取专家 |
| Jev 路由职责 | 使用 TypeSafe Jev 从系统提供的合格候选中先选专家、再选模型；系统保存决策依据与版本 | 为财报提取任务选择专家与可用模型 |
| 专家任务实例 | 专家在某条主线或分支上的一次任务及独立上下文；任务单固定目标、输入和验收条件 | 提取公司 A 的现金流数据 |
| 执行运行 | 某次模型与工具执行，记录版本、用量、状态和错误 | 任务第一次执行、升级后重试 |
| 上下文快照与挂载 | 本次实际使用的指令、消息、资料及结果版本 | 主线截至某条消息的背景 |
| 结果版本 | 不可变的结论、依据、限制、缺失项或产物 | 公司 A 现金流分析 v2 |
| 结果回执与检查记录 | 结果对应的任务单版本、运行、逐项检查及交接资格；与结果一起保存 | 单位检查失败，禁止用于跨公司计算 |
| 结论回传记录 | 选定内容从某个结果版本进入目标对话的关系 | 将插件方案的两条建议带回主线 |

一个专家可以服务多个分支；一个分支可以组织多个专家。相同专家处理不同公司或研究时，任务上下文独立。可复用的是方法与获准经验，不是所有历史任务的数据。

从用户视角，一个分支像一个持续可对话的子智能体；实现上保存分支状态，按需执行专家，无需维护永久在线进程。主线和分支的协调职责可以复用同一协调能力，不必为每条分支创建一种新专家定义。

## 4. 统一对话入口与消息路由

建议规则：先确定消息所属主线/分支，再确定执行专家。主线/分支切换决定对话上下文；指定专家决定本次处理者，两种选择不能混为一项。

| 用户操作 | 系统行为 |
|---|---|
| 在主线发送普通消息 | 主助手理解目标，自行回答或组织专家执行 |
| 选中分支后发送消息 | 在该分支上下文中继续，由其协调者处理 |
| 明确指定专家 | 将原指令交给指定专家；主助手协调记录，不静默更换接收者 |
| 未指定专家 | 主助手形成任务要求，Jev 根据职责、难度、资料范围与预算选择专家和模型 |
| 要求多专家分析 | 主助手拆分子任务与依赖，Jev 为各任务选择专家和模型；调度器组织并发与顺序执行 |
| 要求从某条消息分支 | 固定分叉点与获准背景，建立独立探索空间 |

路由不授予新权限。指定专家能力不足、工具不可用或输入缺失时，明确说明原因，并在既定策略内处理可完成部分；需要用户决策的关键歧义再询问。

建议普通对话默认留在当前路径。主助手可建议创建分支，用户明确提出或接受建议时才生成长期可见分支；后台专家调用不自动变成研究树节点。用户可一次授权探索多个方向。

## 5. 专家协作与模型路由

### 5.1 专家职责

首批专家建议围绕可检查任务定义，避免只有宽泛角色名称。下表是起始方案，数量与边界由案例验证决定。

| 专家 | 输入与职责 | 输出与检查 |
|---|---|---|
| 资料搜索 | 根据问题找到候选来源，核对主体、时间和相关性 | 来源清单、取得的资料、缺口；检查可访问性与来源匹配 |
| 数据提取 | 从明确资料中提取字段、期间、单位和位置 | 结构化数据与原文位置；检查字段与口径 |
| 分析与校验 | 使用工具计算、比较，检查冲突与缺失 | 指标、计算过程、异常与限制；确定性部分交给程序 |
| 综合与探索 | 结合已有结果形成解释、方案、假设和比较 | 结论与依据、反例、假设和待解问题 |

协调者按第 5.3–5.6 节准备专家任务单和获准上下文，专家提交结果回执，系统检查后才允许交接。首版须记录来源定位与检查状态；Stage 5 才能承诺完整证据支持验证，不能把字段齐全当作事实已经核实。

并行专家默认不共享过程。需要交叉检查时，协调者将获准的具体结果版本传给另一专家；这是新的一轮执行，有次数与预算限制。汇总必须保留实质分歧、失败项和证据不足，不能把多数意见直接当作事实。

### 5.2 Jev：专家选择、模型路由与升级

用户确定由 Jev 承担专家和模型选择。这里指 TypeSafe 的 Jev 决策模型：输入状态和类型化问题，返回 Choice、Score 或 Noul 等结构化判断。它不生成自由文本；本产品首版使用 Choice 进行有明确候选的选择，规划、写作和复杂论证由主助手与专家完成。[官方定义](https://docs.typesafe.ai/introduction)

| 参与方 | 职责与边界 |
|---|---|
| 主助手/分支协调者 | 理解用户意图，确定当前分支，拆解任务与依赖，准备目标、交付和验收要求；组织交接、汇总结果 |
| Jev | 从合格候选中选择专家或模型，返回选择、概率分布与 confidence；重选时使用任务与检查反馈 |
| 系统与调度器 | 核验候选可用性、权限、工具能力与预算，固定路由记录，控制并发、执行、取消与提交；拒绝不符合约束的路由 |
| 专家 | 在任务单范围内执行并提交回执，不自行更换验收条件或扩大权限 |

**采用两步路由。** 主助手负责拆分任务，Jev 不在一次选择中同时决定任务拆分、专家数量、执行顺序和全部模型。

1. 主助手准备任务目标、必要上下文、交付和验收要求，固定用户明确指定的专家或模型等约束。
2. 系统从专家目录中筛选职责、工具、权限符合要求且至少存在一个合格执行模型的专家。目录维护专家当前已发布的方法版本，不让 Jev 随意选择历史版本。
3. Jev 从候选专家中选择一个。用户已指定专家时跳过此选择；系统仍检查其是否满足要求。仅有一个合格候选时直接采用并记录规则决定，不产生不必要的 Jev 调用。
4. 根据所选专家的工具、上下文和输出契约，系统筛选实际可用的执行模型；Jev 再从这些模型中选择。用户指定模型和唯一候选按相同规则处理。价格计算、上下文容量和权限判断由程序完成。
5. 主助手结合专家契约补齐任务单，系统重新检查并冻结任务单、实际输入与路由记录，再交给调度器执行。输入装配后若超出所选模型容量，须重新检查和路由，不能静默截断必需资料。

专家契约若与用户要求冲突，须重新协调，不得为了适配候选而降低要求。主助手自身使用已配置的模型，首版不递归调用 Jev 为 Jev 或每条普通聊天重新选模型。

**路由输入和记录。** Jev 接收足够用于选择的任务摘要、输出/验收要求、相关能力描述与必要失败信息，不默认接收整个分支历史、原始文件或工具输出。发送到 Jev 服务的摘要也须符合当前资料对外处理范围；无法提供足够的获准信息时停止该次自动选择。

候选能力与价格来自受控目录和验证记录，不由用户上传材料中的指令修改。首版不要求 Jev 凭模型名字猜测性能，也不把价格最低等同于任务总成本最低。未知能力不视为已支持，预算约束下未知价格不按零成本处理。

系统保存任务单版本、路由输入快照、候选与排除原因、问题/策略/目录版本、Jev 模型版本、原始选择与概率、最终执行选择及路由耗时/用量。路由记录继承输入的访问限制。给用户的说明由这些记录生成；不要求 Jev 输出自由文本理由，也不将说明冒充其内部推理。confidence 不直接当作任务成功率。

**任务内保持稳定。** 独立任务开始时路由，同一任务中的“继续”“按第二种方案修改”等续接默认保持专家和模型。只有任务要求改变、检查发现能力不足或所选模型不可用等明确事件才重新判断。主助手提供包含必要前文的任务摘要，不把短回复独立分类为简单任务。

**异常与重选。** 系统先处理空候选、能力和预算约束；Jev 的候选中提供“无法匹配/信息不足”选项。选择该选项、决策不满足经评测确定的阈值、返回无效候选或 API 失败时，记录为未完成路由，不启动一个未经核验的模型，也不静默改用最贵或最便宜模型。协调者优先补齐已有获准信息；仍不能解决时展示阻断原因和可选处理方式。用户只在确需改变要求或做出决定时介入。网络重试和语义重选分开计数，均受固定次数与总预算限制。

升级模型在相同任务单下创建新运行；若需更换专家或方法版本，则更新任务单并重新检查。重新路由保留原任务、失败历史及累计预算，不重置限额。Jev 不负责决定用户是否采用结论，也不因路由而创建分支。

**参考项目与最小落地顺序。** 以下项目已阅读官方文档或仓库说明，尚未完成代码审计和本地运行，不作为已验证依赖。实现前按现有技术栈核对可复用模块、许可、依赖及测试，不整体接入多套路由运行时。

| 参考项目 | 本产品采用的思路 | 实施顺序与边界 |
|---|---|---|
| [BillionsBobby/JevRouter](https://github.com/BillionsBobby/JevRouter) | 候选能力描述、决策与执行分离、路由回执 | 优先参考专家选择；本产品分别选择专家和模型，不将所有工具和专家混成一个执行计划 |
| [prismhq/jev-router](https://github.com/prismhq/jev-router) | 能力预筛选与多模型调用层分离 | 优先复用项目已有模型接入能力；需要多提供商统一调用时再评估其 LiteLLM 接法，不照搬静默回退策略 |
| [win4r/pi-jev-router](https://github.com/win4r/pi-jev-router) | 任务边界、续接保持、切换成本和实际变更记录 | 首版采用任务内稳定原则；不引入 Pi 宿主及其完整扩展 |
| [AIGNLAI/ReflexRoute](https://github.com/AIGNLAI/ReflexRoute) | 用相似任务的历史表现辅助模型选择 | 首版先积累可信回执；后续评测证明有收益才加入历史检索，不提前建设学习系统 |
| [TokenTrim/jev-routing-experiment](https://github.com/TokenTrim/jev-routing-experiment) | 固定数据划分、成本质量比较与移除 Jev 的消融 | 用于验证路由的真实收益，不将仓库基准结果直接套用于个人研究场景 |

首个闭环只包含少量专家与已核验模型、两步选择、程序约束、运行记录和交接检查。后续历史证据按“任务类型＋专家方法版本＋模型配置”归档，区分来源问题与执行错误；经核验且获准使用的案例才参与检索。历史检索改善选择属于路由策略改进，不等于 Jev 权重训练或专家方法自动进化。

确定方向是任务级差异化模型分配；以下为建议策略：

- 明确、范围小、可程序检查的任务优先评估经济模型；复杂推断、冲突消解和开放探索优先评估能力更强的模型。
- “搜索”与“总结”只是任务标签，不固定等同于低难度或高难度。路由还看材料复杂度、错误代价和质量要求。
- 普通计算、格式校验等由工具完成；模型负责适合其处理的理解与判断。
- 输入质量差、工具失败、缺证与模型能力不足分开诊断；前几类问题不能仅靠更换昂贵模型解决。
- 升级由可记录的检查失败、任务难度或复核结果触发，不只依赖模型自报置信度；禁止无限升级和重试。
- 每次运行固定专家方法、模型配置和路由策略版本。升级产生明确的新执行记录，不悄悄更换运行历史。
- 支持的模型必须通过所需工具、结构化输出与限制契约测试；未通过则不可路由，不通过静默协议回退伪装支持。

成本按完整批次统计，涵盖协调、所有专家、重试、升级、复核和最终汇总。达到限制时保留结果，显示已完成部分与停止原因。并发数、金额、模型名单、升级阈值及重试次数仍待试跑冻结；此前讨论的数字是起始建议，不在本文认定为用户确认参数。

### 5.3 专家任务单：先说明交付什么，再选择如何执行

主助手在分派专家时自动生成任务单，用户继续用自然语言表达目标，无需填写表单。直接回答的普通聊天不强制创建任务单；需要委派、依赖其他结果或独立验收的工作才形成专家任务。后台任务不自动创建长期分支。

一张任务单对应一个负责专家和一个可检查的交付目标。多人协作由协调者拆成关联任务；专家发现超出职责的工作时返回缺口，由协调者决定补派任务，不自行无限增殖下属。

| 内容 | 必须说明什么 | 主要责任 |
|---|---|---|
| 身份与归属 | 任务 ID、所属项目和主线/分支、上级任务、任务单版本 | 系统生成并保存 |
| 用户意图与目标 | 原始要求、预期交付、必须保留的约束、不在本次范围内的内容 | 协调者整理；关键歧义由用户决定 |
| 负责专家 | 专家身份、职责和方法版本、任务类型 | Jev 按任务要求选择，系统核验 |
| 输入与依赖 | 输入快照、资料/结果的准确版本、必需依赖、可选资料、缺失或部分结果的处理规则 | 协调者装配，系统核对 |
| 权限与工具 | 可读取资源、可使用工具、允许的输出位置与操作范围 | 系统按当前权限强制执行 |
| 交付格式 | 表格字段、报告结构或方案要素，来源、假设、限制与缺失项的表达要求 | 协调者复用专家输出契约 |
| 验收条件 | 编号条件、检查方式、检查者及需要的证据；区分阻断条件和提示项 | 协调者在执行前固定 |
| 执行限制 | 时间与成本预算、重试/升级上限、停止条件、模型路由策略版本 | 系统执行限额与调度 |

任务单保存 Jev 采用的路由策略；派发前由 Jev 确定实际专家与模型，系统核验后由运行记录固定模型配置及选择原因。专家不能修改自己的验收条件、扩大权限或突破预算。

目标、必需输入或验收条件发生变化时，创建新的任务单版本；相同任务单的失败重试、模型升级产生新的运行记录。任务身份与历史保留，不能通过新建同义任务清空失败记录或重置总预算。失败历史可供审计，但未经筛选的旧执行上下文不自动进入新运行。

### 5.4 上下文交接：传递够用的信息，并保留边界

借鉴参考项目的任务上下文投影：从所属对话和已授权资料中，装配本任务需要的内容。交接包随任务单固定版本，包含：

- **必须知道**：目标、硬约束、已确定的相关决定、必需输入和使用限制。必须提供正文或可读取的准确引用；缺少必需条件时不派发。
- **可选参考**：有帮助但缺失不影响基本交付的背景、其他方案与可选来源。允许按需读取，缺失只提示。
- **尚未确定**：假设、未解问题、相互冲突的信息及其来源；不得把假设改写成用户决定。
- **来源与版本**：每份资料、结果、决定的来源、版本和依赖关系，以及本次允许使用的范围。

系统记录实际装配和读取的输入。资源已挂载只说明可供读取，不能据此声称专家已阅读或理解；模型是否正确理解由结果检查验证。引用文件存在也不等于内容适用或权限有效。

主助手已知的信息仍须经过范围检查才能交给专家。专家之间只传递获准的结果版本与必要前提，不共享全部聊天历史。派生摘要和结果同样检查来源依赖；交接包不是新的授权凭证。缺失项优先从已有获准资料补齐，只有需要用户决定的歧义才打断用户。

### 5.5 三个检查点：能否开工、是否交付、能否接力

| 检查点 | 检查内容 | 检查后的行为 |
|---|---|---|
| 派发前 | 目标和验收条件明确；必需输入可读；依赖状态符合要求；专家、工具和预算可用；执行依赖无环 | 就绪才运行；缺资料、待决策、权限拒绝分别记录原因 |
| 提交时 | 输出格式、逐项验收证据、来源/口径、缺失和冲突、运行与输入版本匹配 | 标记通过、部分交付、需返工或拒绝；全部保留检查记录 |
| 交给下一专家或带回主线前 | 当前权限、选定内容的必要前提、依赖版本、接收任务要求和目标分支版本 | 符合才建立挂载/回传关系；不符合则阻断相关步骤并说明原因 |

检查职责分开：程序核验格式、权限、版本、预算和可确定的计算；指定的校验专家评估语义、论证与证据支持；用户决定是否采用结论。模型自报“已通过”和文本中出现“测试成功”不能替代程序结果或独立检查。语义检查本身也可能出错，须保留依据与不确定性。

运行结束、交付合格和用户采用是三个不同状态。任务“执行完成”不意味着检查通过；取消、超时、预算耗尽也不构成成功依赖。检查汇总保留全部问题，不用一个通过标记掩盖权限拒绝或缺证。

部分交付可以保存和展示，但下游是否可使用由任务单预先约定。未明确允许时，必需依赖须通过；允许部分结果时，缺失字段及限制必须随结果传递，禁止把未知填成零或把未核实结论当事实。纯探索任务可接受明确标注的假设，其引用的外部事实仍单独核查。

### 5.6 结果回执、返工与提交规则

专家提交独立的结果增量，不直接改写父摘要、其他专家上下文或主线决定。每份结果回执至少包含：

| 回执内容 | 规则 |
|---|---|
| 对应关系 | 任务 ID、任务单版本、运行 ID、专家方法、实际模型和输入版本 |
| 交付内容 | 发现/结论、产物引用、来源位置、假设、限制、冲突和未完成项 |
| 验收明细 | 对每个验收条件说明结果与依据；专家自检和系统/校验专家检查分别记录 |
| 执行情况 | 工具错误、偏离计划及原因；用量、时间和成本来自运行记录，无法取得时标记未知 |
| 后续建议 | 需补充资料、需用户决定或建议续研的具体事项；建议不自动获得执行授权 |

返工按失败原因处理：输入缺失返回上游补资料，解析/工具失败修复对应环节，格式错误在预算内修正，能力不足按策略升级，权限拒绝停止相关工作。每次修正创建新的运行和结果版本；不得覆盖失败证据或在执行后降低验收条件。复核次数与重试共同受任务和整体预算约束。

结果、回执、检查结论和输入依赖作为一个提交单元原子保存；通过检查且保存成功后，才显示“交付通过”并解锁相应下游。部分交付、需返工和拒绝也保存为明确的非成功记录。保存失败显示“待保存/保存失败”，重试保存不重做模型调用。

提交和交接核对当前任务单版本、目标分支修订及有效运行身份。被取消、被新版替代或权限已失效的迟到执行不得发布为有效成果；重复提交同一运行不生成重复结果。回传关系单独原子提交，不能出现界面显示已带回而来源关系未保存的状态。持久化提交属于 Stage 1 的核对范围，跨进程恢复继续属于 Stage 6。

### 5.7 贯穿示例：现金流提取如何交给分析专家

以下为规则示例，不代表真实公司数据或已执行结果。

1. 主助手为公司 A 创建提取任务单：从指定报告版本提取报告期、经营现金流、资本开支及单位，附原文位置；本次不判断竞争优势，也不读取 B/C 的独立过程。
2. 派发前确认报告可读、解析版本可用，固定专家方法与模型。验收条件包括主体/期间一致、单位可定位、各数值有来源；缺失值必须显式返回。
3. 提取结果缺少资本开支单位。回执说明其余字段已完成、该字段未满足条件；检查标记部分交付，保留成果。依赖它的跨公司数值比较不能据此计算。
4. 主助手安排获准范围内的定向补查。若需要新资料，更新任务单输入版本；若只是重读原资料，则在同一任务单下新增运行。预算耗尽时结束补查并报告缺口。
5. 新结果通过检查后，分析专家挂载该准确版本。工具计算和综合报告保留来源与限制；其他公司的独立任务不因 A 的返工重复执行。
6. 用户将分析带回主线时，再检查接收范围与当前权限；带回供讨论不等于用户已经采用。

## 6. 分支、上下文与结论回流

### 6.1 继承和隔离

分支继承分叉时的获准上下文快照，保留消息截止点与资料/结果版本。继承可以通过只读挂载和按需读取实现；不要求每次请求复制全部正文，也不能将摘要压缩表述为逐字保留全文。

| 信息流 | 默认规则 |
|---|---|
| 主线 → 分支 | 固定分叉时背景；主线后续变化不自动注入 |
| 主线/分支 → 专家 | 任务所需的获准背景、资料和指令 |
| 专家 → 所属对话 | 返回成果、来源、限制、失败与缺失 |
| 专家之间、兄弟分支之间 | 不共享过程；按任务显式传递选定结果 |
| 分支 → 主线 | 回传选定结论及来源，保留原分支 |

专家任务在同一任务内可持续多轮；跨任务默认创建独立上下文。长期方法与当前任务资料分开保存。主助手读到某条信息不等于可以转交给所有专家。

“父摘要是源文件，子结果是便签”：父结果版本只读，子结果独立存储，不自动合并。混合摘要包含本节点排除内容时，首版整份拒绝挂载；需要其他部分时，从获准来源生成可追溯的过滤版本。

固定快照不能覆盖当前权限。范围或权限变化后，对受影响上下文停止旧执行、阻止迟到发布，重新装配干净输入。历史成果的访问同样检查来源依赖。

### 6.2 结论回传与更新

用户可从分支结果中选择结论带回主线。回传保存来源分支、结果版本、选定内容和必要的依据/限制；不能只带回有利句子而遗漏改变结论含义的前提。

建议区分“带回供讨论”和“明确采用”。前者提供材料，不自动改写主线已有决定；用户明确采用后再记录采用关系。若与主线现有判断冲突，显示冲突供讨论。

分支或上游结果产生新版本时，旧输入保持不变；系统根据实际依赖提示“来源有更新”，不直接声称旧结论已错误，也不自动重算全部下游。用户或已授权计划决定同步与定向复核。主线更新反向同步到分支时同样固定版本，避免循环同步与无限触发。

展示父子关系与实际输入依赖分别保存。一个比较结果可以使用多个分支版本；画布位置不决定权限和输入。历史结果版本之间可引用，待执行计划必须无环。

## 7. 两个贯穿场景

### 场景 A：公司研究、多模型专家与新分支

1. 用户上传三家公司同一报告期材料，请求比较现金流与竞争风险，并允许联网补充。
2. 主助手确定所需字段与口径，生成搜索和提取任务单，通过派发前检查后运行。三家公司并行执行，相同专家的任务上下文分别隔离。
3. 搜索与清晰字段提取使用通过评测的经济模型；复杂表格或主体/期间冲突按策略诊断、补资料或升级。程序完成数值计算与一致性检查。
4. 提取回执经过逐项检查，符合接收要求的结果才交给分析和综合专家。综合专家使用适合复杂分析的模型，生成比较表与报告，保留缺失数据和不同解释；最终成本包含全部调用。
5. 用户从公司 A 的分析中创建“海外业务是否可持续”分支，继承选定背景及公司 A 结果，不默认读取公司 B/C 的独立过程。
6. 分支内并行组织来源搜索和风险分析，用户可以在同一窗口继续追问或指定专家。
7. 用户将选定结论与限制带回主线，主助手更新讨论；重新出报告时创建新版本。
8. 用户发现一个单位错误，反馈绑定到具体结果、专家方法和模型版本。错误进入待核验案例，不自动覆盖线上方法。

### 场景 B：头脑风暴与独立方向探索

1. 用户提出产品想法，主助手组织技术、体验等必要分析任务，形成结果 1，保留分歧。
2. 用户以结果 1 为共同背景，分出“浏览器插件”和“独立应用”两个方向。
3. 两个分支分别固定结果 1 的版本，独立对话；每个分支都可以调用多个专家，并行推进。探索任务单约定方案要素、约束、反例与未知项，不用确定性事实任务的标准要求创意必须被证明正确。
4. 主线新增约束时，分支不会自动继承；用户明确同步选定约束后，新执行使用新输入快照。
5. 用户要求比较两个方向时，比较任务明确挂载双方结果版本，再选择结论回到主线。
6. 创意明确作为假设或方案表达；其中引用的外部事实另行追溯，不为每个创意伪造证据。

## 8. 专家独立进化

每个专家拥有自己的方法版本、任务级评价标准与经核验案例。独立进化指“改进候选经验证后发布”，不等于每次聊天都自动修改自身，也不等于保存历史就改变了模型权重。

建议首轮允许改进任务指令、示例、查询策略、工具使用顺序和输出检查步骤。模型选择策略可单独版本化评测。专家不能通过进化扩大权限、改变用户目标或修改任意生产代码；模型微调不属于初始范围。

流程：任务记录与反馈 → 核验并归因 → 脱离原任务敏感事实形成获准案例 → 生成候选 → 冻结输入比较新旧方法 → 留出任务验证 → 检查端到端影响 → 受控发布 → 可回退。

例如，提取专家反复弄错“元/万元”，候选增加单位定位与检查。若在不同财报中提高正确率，且成本、耗时与兼容的输出契约满足门槛，才启用新版本。不能把某家公司当次的数字作为通用经验写入所有任务。

反馈分别归因到来源、解析、专家方法、模型、路由或汇总，不因最终答案错误就同时修改全部专家。一次改进尽量控制变量，避免同时换模型和提示词后无法解释收益。

任务单与回执提供归因依据：区分任务交代不清、交接遗漏、执行错误和验收漏检。每项反馈绑定任务单、输入、专家方法与运行版本；专家不能通过删掉失败验收项来制造进步。检查器自身也需要评测，避免把旧检查器的误判固化为训练或改进目标。

在途任务固定旧版本，新任务采用发布版本。用户偏好与专家方法分开：前者描述“我喜欢什么”，后者描述“如何完成任务”。具体候选审批方式、频率与数值门槛待确认；未确认前建议只生成可查看候选，不自动发布。

## 9. 界面与用户控制

主界面以聊天为中心，清晰显示当前主线/分支。分支入口使用思路标题；专家活动显示在所属对话内，可展开查看任务、状态、来源和结果。研究树作为导航与回看视图按需展开。

专家活动默认只显示任务目标、处理者和状态；展开后可查看任务单、输入、逐项回执、检查依据与返工原因。缺少必要信息时由主助手提出具体问题，已有内容不要求用户重复填表。界面分别展示“执行结束”“部分交付/交付通过”和“已采用”，防止混淆。

核心操作：发送目标、指定专家、创建分支、切换分支、查看或调整挂载、停止执行、续研、选择结论带回、标记纠错。用户无需逐个转发材料或设置 Agent 生命周期。

方法管理作为进阶视图展示专家职责、当前方法版本、模型策略、评测变化与回退入口。普通聊天只展示有助于决策的信息：谁在处理、采用了哪些输入、部分失败、费用/时间限制和待决定事项。

“正在生成”“正在保存”“已完成”区分展示；只在必要数据原子提交成功后显示已完成。页面通知失败不重做模型调用，取消保留已提交成果，迟到结果不能覆盖新结果。跨进程自动恢复属于持久执行阶段。

## 10. 验收与效果衡量

| 维度 | 应证明的行为或指标 |
|---|---|
| 专家专精 | 同类固定任务的正确率、字段/格式合规、来源匹配与缺失识别 |
| 上下文隔离 | 输入和工具返回不出现未挂载任务的唯一标记；历史与缓存同样受控 |
| 专家与模型路由 | 先选专家再选模型；用户指定不被覆盖；唯一候选免调用；能力/权限/预算预筛选；两步记录可追溯；续接不随意换模 |
| 路由异常 | 空候选、信息不足、低确定性、Jev 超时/无效结果均不启动未核验模型；重试有界；输入装配后超容量重新检查 |
| 多专家协作 | 真正有界并发，结果对应原任务；局部失败与分歧保留 |
| 任务与交接 | 必需输入缺失不派发；取消依赖不算成功；部分结果不越过接收条件；交接保留前提、范围及准确版本 |
| 检查与提交 | 自报成功不能冒充检查通过；失败可追溯；原子保存失败不解锁下游；重复提交不重复产出；旧运行不能覆盖新版 |
| 分支体验 | 从分叉点继承背景，独立多轮探索，选定结论回传，来源可查 |
| 成本与速度 | 全链路费用、重试/升级率、等待与总耗时，含失败运行 |
| 进化 | 候选隔离、留出集验证、版本回退、跨专家连通不退步 |
| 用户负担 | 重复说明背景、手工转发、寻找上下文的次数，以及分支操作负担 |

建议对同一材料与目标比较：单 Agent 基线、相同专家分工使用统一模型、相同分工使用混合模型。按可用预算选取必要对照，分别判断分工和路由的贡献。质量门槛、案例数量和允许成本须在验收前冻结，不能看完结果再更改标准。

Jev 路由单独验证：固定任务拆分、专家方法与候选池，比较固定模型、确定性规则路由、Jev 路由；加入历史证据后，再比较“仅历史证据”和“Jev＋历史证据”。专家选择准确性与模型选择收益分别计量，最终检查整个研究任务的交付质量、总成本和耗时，包括两次路由、失败、重试、复核及上下文切换。保留独立测试任务，覆盖中文研究指令、依赖前文的短回复、复杂表格与开放探索。阈值在开发样本上确定，不能用测试结果反复调整。

参考实验已出现“历史证据带来收益，但 Jev 未增加可测收益”的情况，因此验收不能仅证明接口能调用或选择格式正确。[实验及消融说明](https://github.com/TokenTrim/jev-routing-experiment) 若未达到预先冻结的质量与成本门槛，记录差距并修改候选描述、任务摘要或选择策略后重测，不宣布自动路由达到产品验收标准。

“经济模型经专精后更强”“混合路由更省钱”“多个专家更可靠”均需真实任务验证；脚本测试只能证明控制契约，单次模型成功不能证明稳定改善。

## 11. 实施路线与现有基础

当前开发顺序为：保留 Stage 0–4 基础 → R1 任务单与检查交接 → R2 Jev 两步路由 → R3 统一聊天与分支回流 → Stage 5 证据 → Stage 6 恢复 → Stage 7 评测 → Stage 8 方法版本 → 可选 Stage 9 记忆 / Stage 10 专家进化。R1–R3 是进入 Stage 5 前的补齐里程碑，不重命名历史阶段。详细交付与起始执行默认值见[新开发文档](./当前产品-增量开发与技术选型.md)；下表说明能力归属，不表示直接跳过补齐工作。

截至本次整理，README 与 Stage 4 验收记录记载 Stage 0–4 已完成，包括基础执行、持久记录、并发、资料范围、节点与固定结果版本；本文仅核对这些记录，未重新运行测试或审计全部实现。这不代表最新产品目标已全部满足。

| 阶段 | 本轮目标对应 | 后续核对重点 |
|---|---|---|
| Stage 0–1 | 专家执行入口、独立输入、会话与原子记录 | 任务单与运行分离，结果/回执/检查/依赖原子提交，保存重试与迟到发布保护 |
| Stage 2 | 专家路由、并发、结果收集 | Jev 两步选择、候选预筛选、任务内保持、路由异常与版本记录；任务单派发、依赖与部分交付、全链路成本 |
| Stage 3 | 资料与任务上下文隔离 | 交接包装配、实际读取记录、当前权限强制执行，覆盖同一专家跨任务及派生信息 |
| Stage 4 | 分支与多专家融合体验 | 核对从消息分叉、持续对话、专家选择、选择性回传及采用关系；交接版本与目标修订检查；现有节点比较不等同于完整体验 |
| Stage 5–6 | 证据链、长任务可靠执行 | 回执证据支持验证，证据绑定结果版本，恢复不越权，不重复提交 |
| Stage 7–8 | 专家评测与版本化方法 | 任务单/回执驱动归因，检查器评测，专家方法与 workflow 分别管理，建立固定基线 |
| Stage 9 | 可管理偏好与经验召回 | 用户偏好、专家方法和任务事实分离；不作为进化前提 |
| Stage 10 | 专家独立进化与发布 | 分专家质量门槛，加跨专家端到端检查，发布和回退可控 |

下一个产品验收重点应是“分支＋专家并发＋任务级模型路由”的完整链路。自主进化是后续目标，先确保专家有明确版本、反馈归因和可评测输出，不提前搭建完整自动优化系统。

继续执行用户已确认的方法：优先复用可靠参考实现与已有依赖 → 跑通最小链路 → 对照设计逐项识别 gap → 最小修改补齐 → 本阶段与前序连通回归 → 真实交互验收。参考项目按能力借鉴，不等于同时引入多套 Agent 引擎。不为新产品设计预留无限兼容层，也不因概念调整推倒已验证基础。

## 12. 尚待决策的细节

- 首批专家名单及职责粒度：优先围绕两场景建立少量可测能力，尚未确定固定数量。
- 模型候选、价格配置、并发/预算与升级阈值：需实际样本验证，不预设贵模型永远更好。
- Jev 接入配置：具体 API 提供方、固定模型版本、超时/重试上限及决策阈值在最小链路试跑中核验并冻结；参考仓库模块是否复用须经代码与许可检查。
- 分支默认继承完整可访问历史还是经核对的摘要加按需原文：需平衡理解完整性、成本与交互透明度。
- 结论回传的选择粒度、采用状态和通知频率：需验证是否减少负担，避免把思考变成繁琐审批。
- 专家进化的发布权限、触发频率与最低样本量：在评测基础建立后明确。
- 部署形态与长期运行方式：已有记录描述个人本机应用，尚未据此决定目标产品只能本机或必须云端。

这些细节不改变当前主方向：独立任务上下文与专精专家作为能力基础，路由选择合适模型，分支承接用户的新想法，反馈与评测支持每个专家逐步改进。
