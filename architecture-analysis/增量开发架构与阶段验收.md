顺序与原提议的差异：记录提前，作用域先于研究树；执行恢复与“存进数据库”分开；模板复用先于自动进化；长期记忆不是 workflow 的前置条件。测试、基础日志和契约从 Stage 0 开始，Stage 7 增加的是产品反馈与正式评测闭环。

表中的依赖同时标出了本产品的执行与验收前置条件，不能把它们全部理解为必须 import 的模块。尤其是：Stage 8 模板执行的硬依赖是 2、4，Stage 7 是版本质量验收门槛；Stage 9 的上下文接入硬依赖是 3，只有从反馈推导候选偏好才需要 7。Stage 10 不应强制依赖 Stage 9。记录、评测、恢复均通过公开服务接口组合。

## 产品视角：每个 Stage 对应什么功能，为什么设计它

产品面向个人研究者，同时支持用户上传资料与系统联网搜索。公司研究以比较表和报告为最终交付，研究树在探索过程中自然形成。节点表达通用的问题、指令、上下文与结果，也支持头脑风暴后从同一结果分出独立方向。Agent 在节点目标内自主研究，用户分出的节点遵循对应用户指令。Stage 4 定义两个贯穿案例；资料接入与挂载从 Stage 3 开始。

下表回答“这个阶段为用户解决什么问题”；后面的逐阶段设计回答“如何实现与验收”。基础设施阶段也必须服务于明确的产品体验，不要求每个阶段都增加一个独立页面。

| Stage | 对应的产品功能 | 用户实际遇到的问题 | 为什么设计它 | 投资研究场景中的具体表现 |
|---|---|---|---|---|
| 0：Agent Core | **对话式任务入口与基础执行**（基础能力） | 用户用自然语言提出问题，希望系统理解后调用工具、必要时请专家协助，并返回结果。 | 建立从输入到结果的最小闭环；所有后续功能都复用同一执行入口，先验证 Agent 本身能工作。 | 用户提交两组经营数据，让系统计算增长率，再由已注册的分析专家解释结果；此时不承诺自动完成全行业研究。 |
| 1：记录持久化 | **历史会话、运行详情与结果留存**（基础设施支撑的体验） | 用户关闭应用后不想丢失研究成果；出现失败时需要知道执行到了哪里。 | 给每次执行留下可查询记录，使后续研究、反馈和问题排查有明确对象；保存记录与恢复计算分别建设。 | 次日打开应用，仍能查看昨天的分析结果、工具调用和失败位置；未完成任务此时只显示中断。 |
| 2：路由与并发 | **多专家分工、并行分析与结果收集**（执行能力） | 一个问题包含多个可独立分析的方面，串行研究耗时长，也容易遗漏某个方面的结果。 | 让任务分配、并发上限、预算和部分失败成为明确策略，为后续多公司、多维度研究提供执行基础。 | 同时让三个专家分析成本、市场和风险；每份结果对应原任务，某个专家失败不会被汇总悄悄掩盖。 |
| 3：资料接入与作用域 | **资料接入、只读挂载与分支信息隔离**（产品约束） | 用户已排除某行业或公司，但旧分支材料仍可能被带入后续分析；子 Agent 得到过多无关历史。 | 将用户的范围选择落实到输入装配和工具返回边界，控制哪些信息可以流入一次执行，为研究树建立可信的隔离基础。 | 公司 A 的分析只获得获准的行业摘要、A 的材料与适用指令；不自动继承公司 B 的原文和对话。行业相关性另外通过搜索约束与材料筛选控制。 |
| 4：研究树与结果版本 | **可视化探索、独立分支与固定版本比较**（核心产品能力） | 用户不只想收取最终报告，还想理解研究路径、在岔路口作选择，并从任意已有节点继续。 | 把研究过程变成可操作的产品对象，保留问题、选择和结果的关系；避免每次改变方向都重新开始整段对话。 | 展开“行业→公司→财务/竞争”，选中一家公司深入，排除另一家；改变假设形成新分支，旧成果仍可回看。 |
| 5：证据链 | **结论溯源、原文查看与缺证/反证展示**（核心产品能力） | 用户需要判断“为什么认为行业还有增量”“为什么这家公司有潜力”，单独一段流畅总结不足以判断依据。 | 将事实、证据与推断分开保存，使每个重要结论可检查、可质疑、可更新，也为后续质量评测提供依据。 | 点击“海外业务增长较快”查看报告原文、期间和支持片段；材料不足时显示未知，存在冲突时同时展示反证。 |
| 6：持久执行 | **后台长任务、断点续跑与失败重试**（基础设施支撑的体验） | 深度研究可能持续较久，浏览器关闭、worker 重启或短暂工具故障不应导致全部重做。 | 将执行生命周期与当前界面、进程解耦，保存已提交步骤并管理未完成工作，控制重复执行和恢复成本。 | 三家公司已完成一家时 worker 重启；已提交结果保留，剩余步骤继续执行。未提交的外部调用可能重做，恢复边界明确展示。 |
| 7：反馈与评测 | **节点纠错、结果评价与版本效果对比**（质量改善能力） | 用户发现错误后希望系统准确记录问题；开发者需要判断一次修改是否提高了质量。 | 把反馈绑定到具体节点、结果与证据版本，形成可重复评测的案例；区分“用户愿意继续研究”与“结论正确”。 | 用户指出某个增长率引用了错误报告期；该问题进入评测样本，用同一材料比较新旧方法的准确性与成本。 |
| 8：方法复用 | **保存研究模板与复用分析 Skill**（效率能力） | 用户认可一条研究路径后，希望换行业、公司或时间范围继续使用，不想重复安排相同步骤。 | 将可复用的方法从一次性的事实和执行记录中提取出来，形成参数化、版本化资产，为自动进化提供明确对象。 | 把“行业增量→公司筛选→现金流/竞争→比较”保存为模板，换一组公司运行；复用方法，重新获取事实。 |
| 9：长期记忆 | **跨会话偏好适配与记忆管理**（个性化能力） | 用户不想每次都重述分析顺序、来源偏好和表达习惯，又需要能覆盖或删除过去的偏好。 | 将允许长期生效的信息独立管理，通过上下文入口按用户、场景和有效期使用，避免把整段历史自动灌入所有任务。 | 用户确认“公司研究先看现金流”，新会话自动应用并展示来源；本次要求先看竞争格局时覆盖它，删除后不再使用。 |
| 10：方法进化 | **改进建议、验证后发布与版本回退**（持续改善能力） | 用户希望常用方法随反馈逐渐适配自己，但不希望系统悄悄改坏原有流程。 | 将“提出改动”与“采用改动”分开，以固定案例和留出任务验证候选；通过版本发布控制对未来任务的影响。 | 系统提出将现金流检查提前，展示关联反馈、流程差异和质量/成本对比；确认启用后用于新任务，也可回退。 |

### 这些功能如何形成一个完整产品

- **Stage 0–2：能执行任务。** 用户能够提出问题、使用工具并获得多专家结果；此时主要验证执行基础。
- **Stage 3–5：能由用户掌控研究过程。** 用户限定范围、选择研究方向，并检查每个重要结论的依据；这是第一个完整的研究产品里程碑。
- **Stage 6：能可靠完成长研究。** 研究进度不再依赖当前界面和单个进程存活。
- **Stage 7–8：能纠错并复用有效方法。** 用户的纠正可以被验证，成功路径可以再次执行。
- **Stage 9–10：能适配用户并改进方法。** 记忆回答“本次应考虑哪些历史偏好”，进化回答“以后应采用哪个经过验证的方法版本”。

因此，产品的核心闭环是：**提出问题 → 限定范围 → 分工研究 → 用户选择与续研 → 检查证据 → 纠正结果 → 复用方法 → 验证改进**。每个 Stage 都为这条闭环补上一个独立能力，而不是单纯为了引入某个技术组件。

## 一、先明确真正最小的 Core

### 1. Core 的职责

Core 分为小型执行内核和基础会话服务：

- **CoreRunner**：执行一次有边界的 Agent 调用，返回标准化结果，产生运行/工具/委派事件。
- **ConversationService**：读取基础历史，把新用户输入交给 Runner，将已完成的会话增量保存。会话服务和执行循环分开，方便之后由应用层安排事务与持久执行。
- **AgentCatalog**：按稳定 ID 找到已注册的 Agent 定义；不负责研究规划。
- **ToolBinding**：工具名、说明、输入结构和处理函数；返回结构化工具结果。
- **最小委派原语**：调用一个已注册子 Agent，明确提供输入并返回结果。Stage 0 默认串行、深度 1；无自动递归、并发队列或路由图。

用户输入的语义理解通常由模型结合 Agent 指令和工具说明完成。不要在 Core 里先造一套通用 IntentClassifier。若任务需要明确意图结构，可为特定入口 Agent 声明输出模型；业务路由策略到 Stage 2 再实现。

Core 不包含：研究树、行业与公司概念、作用域数据库、RAG、证据索引、长期记忆、偏好、反馈评分、Skill 候选或版本发布。

### 2. SDK 与我们各自负责什么

| 职责 | OpenAI Agents SDK | 自己的代码 |
|---|---|---|
| 模型交互、流式输出、工具调用循环 | Agent、Runner、工具 schema 和内部协议 | 不重复实现循环 |
| 工具和专家的语义选择 | 模型在传入的能力集合中选择 | 决定注册哪些能力，拒绝未知或越权目标 |
| 单 Agent 执行 | Runner.run / run_streamed | 标准入口、期限、错误映射、取消 |
| 最小专家调用 | SDK 可以支持 agents-as-tools | 明确父子 ID、独立输入、深度限制；通过同一 Core 入口执行 |
| 并发和结果收集 | 提供执行原语 | Stage 2 Dispatcher 负责，不放进 SDK adapter |
| 基本会话 | 提供 Session 协议及实现 | 拥有 conversation ID、历史选择与写入规则 |
| 研究状态、业务权限、质量判定 | 不自动提供产品语义 | 后续独立服务负责 |

`Agent.as_tool()` 默认共享底层应用 context，不能把它当成独立上下文隔离。推荐把自己的 `delegate` 注册为工具；其 handler 按 Agent ID 调用 Core 公共入口，传入显式输入，创建子运行，不自动继承父会话。SDK 负责这个工具在模型循环中的调用。之后需要并发时，外层 Dispatcher 重用同一入口。

### 3. Stage 0 必需的契约

以下是架构草图，不是需要立即实现的完整通用 SDK。

```python
class RunRequest:
    run_id: str
    parent_run_id: str | None
    agent_id: str
    input: PreparedInput
    limits: RunLimits

class PreparedInput:
    messages: list[Message]
    # Stage 0 只需规范化 user/assistant 文本。
    # 工具协议在一次运行内部由 SDK adapter 管理。

class RunResult:
    run_id: str
    status: str               # succeeded / failed / cancelled
    output: str | dict | None
    usage: Usage
    error: RunError | None

class RunError:
    code: str
    origin: str               # engine / tool / core ...
    message: str
    retryable: bool
    cause_id: str | None

class EnginePort(Protocol):
    async def execute(self, request, agent_spec, tools, emit) -> RunResult: ...

class ExecutePort(Protocol):
    async def execute(self, request: RunRequest) -> RunResult: ...

class ConversationStore(Protocol):
    async def load(self, conversation_id) -> ConversationSnapshot: ...
    async def append(self, conversation_id, expected_revision,
                     run_id, messages) -> None: ...
```

- `AgentSpec` 只包含 ID、指令、已批准工具集合、输出契约和必要模型配置。后续业务服务准备它的值，Core 不加载 Skill 或偏好数据库。
- `ToolBinding` 的 handler 接收普通应用类型；OpenAI adapter 把它包装成 SDK 工具。
- `RunLimits` 首先包含轮数、超时、委派深度和最大调用次数限制；全任务并发/预算策略归 Stage 2。
- `CoreEvent` 从第一天包含 run_id、parent_run_id、tool_call_id、阶段、开始/完成/失败。工具结果通过标准结构返回，异常不伪装成成功文本。
- 原始 SDK 对象留在 adapter 内，内部存档若需要保存不透明 SDK 状态，使用 adapter 自己的 codec。不要把 SDK 的 Agent/Session/RunContextWrapper 暴露给 research/memory 模块。
- 不增加万能 `metadata/context` 袋子来塞后续所有数据。产品数据通过外部服务生成 PreparedInput，或关联到 run_id；工具的 scope 通过闭包绑定。

**会话最小语义**：默认保存用户输入与最终回答；子 Agent 不共享父 conversation。工具调用事件另存。没有承诺跨引擎重放所有厂商原始 item。换引擎时基础对话继续成立；专有检查点的恢复能力单独评估。

**同一 conversation 的并发**：第一版单写入者，冲突直接返回明确错误；不同子运行使用独立输入。`append` 按 run_id 幂等，避免重试把同一回答写入两次。

### 4. 最小测试替身

Stage 0 同时实现 `ScriptedEngine` 测试 adapter：按脚本请求普通 ToolBinding、返回结果或注入异常。它用于测试我们自己的控制与通信契约，不假装验证真实模型的语义理解。

OpenAI adapter 另有 SDK 映射测试；真实语义效果用少量固定交互测试观察，不对长自然语言回答做逐字快照断言。

## 二、模块依赖与关闭规则

依赖方向：

```text
api / cli / composition
       ↓
research、memory、skills、feedback 等应用能力
       ↓
orchestration / execution 的公共接口
       ↓
CoreRunner → EnginePort ← OpenAI adapter
```

其他依赖同样通过公共接口：ResearchService 请求 ContextBuilder；EvidenceService 通过 ScopeService 校验访问；MemoryService 提供 ContextContribution；WorkflowCompiler 输出 ResearchPlan；EvolutionService 请求 EvaluationService，并通过版本发布接口启用结果。

约束：

1. Core 不导入 resources/research/context/evidence/memory/feedback/skills/durability。
2. 模块不查询其他模块的表；同一个 PostgreSQL 内也遵守所有权。
3. 跨模块写操作通过命令服务，读操作通过查询接口。模块可共享不可变 ID/值对象，不共享可变状态对象。
4. 关键行为走显式调用；事件主要用于追踪、投影和通知。不要让调度、授权和版本发布藏在无序的全局事件订阅中。
5. 第一版普通 Python 调用与依赖注入即可；无需微服务、插件市场、通用中间件 DSL 或消息总线。
6. 每个阶段只创建当前真正需要的接口和目录。下面的最终目录是路线图，不要求 Stage 0 全部建空壳。

### 关闭不是自动降级权限

“每个模块可以关闭”意味着基础 Agent 可以独立运行，不意味着关闭前置能力后下游仍能兑现相同承诺。

| 关闭能力 | 正确结果 |
|---|---|
| 研究树 | 普通对话、工具与基础专家委派继续工作 |
| 上下文作用域 | scoped research 工具及依赖它的研究入口停用；基础无资料权限的 Agent 继续工作 |
| 证据链 | 基础 Agent 可运行；结果不能标记为已验证研究报告 |
| DBOS | 显式使用进程内执行模式；没有重启恢复承诺 |
| Langfuse exporter | 产品反馈仍保存，导出可重放；基础研究不受影响 |
| 记忆 | 不注入历史偏好，基础研究仍工作 |
| Skill/workflow | 使用应用明确配置的基础 Agent；模板入口停用 |
| 自动进化 | 已确认版本照常使用，不再生成/发布候选 |

`composition.py` 在启动时检查启用模块的依赖。遇到无效组合应拒绝启动相关入口，不允许静默改成全库检索或未经验证发布。数据库故障也不自动切回内存模式：基础模式是显式选择的运行配置。

## 三、逐阶段设计

### Stage 0 — 最小 Agent Core

1. **只增加的能力**：一次基础 Agent 执行，以及串行调用一个已注册专家并得到结果。附带最小会话与标准事件。
2. **加入时机**：这是所有业务能力调用的最小内核；如果这里不稳定，后面的质量问题无法与执行问题区分。
3. **依赖/禁止侵入**：只依赖 EnginePort、ConversationStore、工具 handler 和标准事件回调。不出现任何研究或长期记忆类型。
4. **新增模块/接口/数据/表**：`core`、基础 `agents`/`tools`、`adapters/openai`、`adapters/in_memory`、`app/cli`；RunRequest/Result/Error、AgentSpec、ToolBinding、Message、ConversationSnapshot。无数据库表。
5. **不应修改的既有模块**：无；完成后将 Core 契约、基础场景和默认行为作为后续基线。
6. **参考实现**：SDK `Agent`、`Runner`、`Session` 协议和 `Agent.as_tool()`；借鉴原语，自己负责稳定外部接口与显式子输入。
7. **单独测试**：不用模型测试普通回答、一次工具调用、未知工具、工具异常、输出契约失败、超时、取消、委派深度超限、子结果返回和会话冲突。增加真实模型场景检查语义选择是否合理。
8. **回归测试**：建立 C0 套件与调用序列断言；尤其测试模型一次提出 A/B 两个工具时不能执行为 A/A/B。固定输入与脚本引擎结果可确定性比较。
9. **真实交互**：CLI 输入“算出 12×8，再让表达专家把结果说成一句中文”；看见工具、子 Agent 及最终结果；追问“刚才结果是多少”能使用当前会话。
10. **故障定位/回退**：检查 run→tool_call→child_run 时间线；脚本引擎也失败归 Core/工具，只有真实 SDK adapter 失败则检查协议映射或模型。该阶段是独立基础运行模式。

### Stage 1 — 会话与运行记录持久化

1. **只增加的能力**：运行结束后可查询、可重启读取的记录；不增加后台恢复执行。
2. **加入时机**：先获得可靠的观察依据，再测试并发、范围和树。它不会要求提前设计未知的业务表。
3. **依赖/禁止侵入**：包住 ExecutePort，消费 CoreEvent，替换 ConversationStore 实现；不得改 SDK 循环、工具选择或 Agent 提示词。
4. **新增模块/接口/数据/表**：`execution/service.py`、`ledger.py`、`ports.py`；PostgreSQL repositories；RunRecord、StoredRunEvent。表 `conversations`、`conversation_messages`、`runs`、`run_events`。基础 run 已有 parent_run_id，后续树不需要改变它的含义。
5. **不应修改**：CoreRunner、ToolBinding、已有 Agent 与工具；改动集中在 composition、应用会话协调和新 repository adapter。
6. **参考实现**：SDK `memory/session.py` 的 Session 协议、`extensions/memory/sqlalchemy_session.py` 的存储实现。标准会话可借鉴其约束；SDK 原始会话存储若直接使用必须留在 adapter 内。
7. **单独测试**：内存/SQL store 共用契约；重启读取、按 run_id 幂等追加、expected_revision 冲突、事件顺序、存储失败。数据库实现必须原子提交会话成功增量、结果与运行终态；注入提交前失败、提交成功后响应丢失、重复提交和进程退出，验证不会出现成功记录缺少结果或重复回答。
8. **回归测试**：C0 在两种 store 下运行；同一 ScriptedEngine 输入输出、工具序列一致；记录模块不得新增模型调用。
9. **真实交互**：完成一轮后关 CLI，再打开查询同一会话和工具记录。被强制终止的运行显示 interrupted/未完成，不会假装已经恢复。
10. **故障定位/回退**：Core 已产生成功结果而提交失败，定位 execution/repository；SQL 正常但 UI 不显示，定位查询或投影。可以显式启动 in-memory 基础模式；不能在数据库错误后自动丢弃持久语义。

#### 提交边界与用户可见状态

界面依次显示“正在生成 → 正在保存 → 已完成”。流式文字属于未确认保存的预览；只有必要业务数据提交成功，才能显示“已完成”。Core 返回的 `succeeded` 仅表示执行成功，不能直接当作持久化完成通知。

- 应用层协调一次明确的 PostgreSQL 事务，通过各模块公开写入接口共享事务；模块仍不读写彼此私有表。模型与外部工具调用不放进数据库事务。
- Stage 1 在该事务中保存结果、会话成功增量和运行终态。Stage 4 加入不可变节点结果版本、输入依赖和节点当前结果关联；Stage 5 再加入发布所需的引用关系。仅在对应阶段实现这些写入，不提前创建业务空壳。
- 每次提交使用稳定的 `commit_id`，重试复用同一 ID；同 ID、同内容返回已有结果，同 ID、不同内容明确报冲突。会话继续使用 `expected_revision` 检查并发，按 `run_id` 防止重复追加。
- 画布投影、通知和统计不参与结果成功条件，可根据已提交记录重建。它们失败不会撤销结果，也不得触发重新调用模型。
- 原始文件先完整写入内容存储，再由事务登记引用；写入失败不发布引用。事务失败留下的未关联文件可清理，不假设文件系统与 PostgreSQL 之间存在同一个事务。

| 故障位置 | 用户可见状态 | 处理规则 |
|---|---|---|
| 模型或工具执行失败 | 失败，保留已提交的历史成果 | 保存明确的失败原因；不生成成功回答 |
| 已生成结果，提交明确失败 | 保存失败，预览尚未确认留存 | 原结果仍在内存时只重试保存；会话版本冲突不得强行追加 |
| 提交超时，结果不确定 | 正在确认保存状态 | 按 commit_id 查询或幂等重试，不立即重新执行模型 |
| 提交成功，页面更新失败 | 重连后显示已完成 | 从数据库查询或重建投影 |
| 提交前进程退出 | interrupted／未完成 | 未提交内容可能丢失；本阶段不自动恢复计算 |
| 提交后进程退出 | 已完成 | 从已提交记录恢复展示，不能重复追加回答 |

Stage 1 默认单执行进程。每次启动登记唯一的进程实例 ID，启动时确认旧执行实例已退出后，将其未终结运行标记为 `interrupted`；不能仅按耗时长短判定中断。该状态属于运行记录，不要求 Core 增加一种模型返回状态。Stage 6 引入 worker 后，由持久执行服务接管存活判断与恢复。

### Stage 2 — 路由、并发与结果收集

1. **只增加的能力**：基于明确策略分派多个执行，限制并发并收集各自结果。
2. **加入时机**：Core 委派已可用、记录可查询，此时才有条件判断并行是否真的独立且更有效。
3. **依赖/禁止侵入**：只调用 ExecutePort、AgentCatalog 和 RunRepository 的公开接口；不读取 SDK messages，不直接改任何会话。
4. **新增模块/接口/数据/表**：`orchestration/router.py`、`dispatcher.py`、`collect.py`；RouteDecision、DispatchPlan、DispatchItem、ResultSet、DispatchPolicy。新增 `dispatch_groups` 保存计划、输入绑定、完成策略和子 run ID；复用 runs，不建第二套运行表。
5. **不应修改**：CoreRunner、SDK adapter、已有工具、会话结构。可新增 Agent 定义，并在 composition 注册新 Orchestrator。
6. **参考实现**：SDK financial research 示例的 `_perform_searches()`、planner 的结构化计划；不照搬无限创建任务和吞掉错误的行为。
7. **单独测试**：脚本专家返回不同标识；用同步屏障证明同时执行，不靠脆弱的毫秒耗时断言。检查并发上限、父子 ID、结果乱序、部分失败、取消传播、递归限制和预算停止。
8. **回归测试**：C0/C1；单任务经过 Dispatcher 与直接执行等价；非路由对话不能突然多出规划调用。局部失败不得错配结果或被总汇总掩盖。
9. **真实交互**：输入“请三个专家分别比较方案的成本、速度与限制”；CLI 显示三个独立运行，按原维度汇总，其中一个失败时明确显示缺失。
10. **故障定位/回退**：分错专家看 Router；专家本身失败看 child run；结果丢失/错位看 Collector；卡住看 Dispatcher 的活动任务与等待条件。关闭 Orchestrator 后基础串行 delegate 继续可用。

### Stage 3 — 资料接入、上下文作用域与只读挂载

1. **只增加的能力**：接入用户上传和网络获取的资料，保存可定位的内容版本，明确控制一次运行可读取、挂载和写入的信息范围。
2. **加入时机**：研究树之前先建立资料身份与隔离；Stage 5 再增加证据与结论关系。资源层不要求所有资料都有公司或报告期。
3. **依赖/禁止侵入**：ResourceService 负责接入与资源登记；ScopeService 决定访问和挂载；ContextBuilder 生成 PreparedInput，ScopedTool 包装工具。全部经过公开查询接口，不修改 Core context，不让模型决定授权范围。
4. **新增模块/接口/数据/表**：`resources/service.py`、`ingestion.py`、`snapshots.py`、`ports.py`；`context/scopes.py`、`mounts.py`、`builder.py`、`tool_guard.py`。Resource、SourceSnapshot、ParseResult、ResourceRef、ContextMount、RunScope、ContextSnapshot；表 `resources`、`resource_ingestions`、`source_snapshots`、`resource_parses`、`context_scopes`、`context_mounts`、`context_snapshots`。原始内容由 BlobStore 保存，解析器由 adapter 实现。Scope 包含允许资源、允许继承结果、工具集合、版本和预算。
5. **不应修改**：CoreRunner、SDK adapter、Dispatcher 的执行算法；新建资料接入工具、解析 adapter 和范围包装器，通过 composition 组合。
6. **参考实现**：原有 OpenViking 输入装配、Letta 作用域目录及 SDK context；补充参考 GPT Researcher 的混合资料接入、PaperQA 文档身份、Docling 解析，以及 Deep Agents 文件工具与独立子上下文。具体链接与采用边界见本节末尾。
7. **单独测试**：A/B 唯一标记隔离、伪造资源 ID、空范围、父历史污染、混合摘要拒绝挂载、范围切换、写入归属、缓存隔离；解析失败、扫描件、部分成功、内容去重、同名不同内容、URL 内容更新；只读挂载、版本固定、撤权后禁止继续读取。用真实文件验证解析 adapter，不能只测预制解析产物。
8. **回归测试**：C0–C2；普通工具基础行为不变，并行任务互不改 scope。同一 conversation 改范围后重新装配干净上下文，禁止继续使用含被排除资料的历史。程序验证注入与工具返回边界，真实模型评测语义相关性。
9. **真实交互**：上传 A/B 两家公司材料并联网补充；看到解析状态、资料版本和当前挂载。选择只研究 A 后，B 的原文、搜索摘要及混合父摘要不进入本次上下文；扫描件显示 OCR 处理状态，解析失败可定位原因。
10. **故障定位/回退**：文件不可用看接入/解析；资料归属错误看 ResourceService；越界看 ScopeService、Builder 或 ScopedTool。关闭范围模块同时停用 scoped research 入口，不能静默扩大权限。

#### 资料接入的责任与生命周期

| 环节 | 负责方 | 保存或校验的内容 |
|---|---|---|
| 上传 | 用户通过入口提交，后端接收 | 所属用户与研究范围、原文件名、上传时间；Stage 3 可用 CLI/API，Stage 4 再增加页面 |
| 搜索与抓取 | Agent 发起，受控工具执行 | 查询、标题、URL、摘要、实际访问地址和抓取时间 |
| 存储与登记 | ResourceService | 资源 ID、原始内容、内容哈希、接入记录和不可变快照 |
| 解析 | Parser adapter | 正文、表格、页码或位置、解析器版本/配置、成功与失败范围 |
| 属性提取 | 程序与专用提取步骤 | 候选属性、提取依据、校验状态及用户纠正记录 |
| 授权与挂载 | ScopeService | 当前访问权限、目标范围、只读挂载及固定版本 |
| 形成证据 | Stage 5 EvidenceService | 具体片段与结论的支持、反对或缺证关系 |

搜索发现时先登记发现记录：标题和摘要也是外部信息，返回给研究 Agent 前必须经过范围检查。抓取正文后保存正式 SourceSnapshot，解析可用且通过授权后才可挂载正文。发现记录不能冒充已经读取的原文证据；资源存在、允许访问和支持结论分别判断。联网已获用户允许时，程序按范围规则自动接入普通搜索结果，无需逐条确认。默认只加入发起搜索的范围，不自动向其他分支开放。

系统填写哈希、上传/抓取时间和实际 URL。公司、报告期、币种、单位及合并口径由提取步骤生成候选，并保留原文位置；程序检查格式与一致性。文件名仅作线索，发布日期不等于报告期，一份年报中的不同年度数字分别绑定期间和单位。用户要求“同一报告期”是待校验条件；影响比较的冲突标记并请求处理，不能用猜测补齐。通用头脑风暴资料不强制填写公司属性。

解析状态为 `pending / processing / ready / partial / failed`。扫描页进入 OCR，保留原图和页码定位；部分成功只允许读取成功且可定位的部分，显示缺失范围；失败保留原文件与错误，不以空文本冒充成功。重复内容按哈希复用存储；仅在内容与解析器版本/配置一致时复用解析产物。每次上传/抓取仍保留独立接入记录和授权关系，去重不能扩大权限。同名不同内容、同 URL 内容变化保存不同快照，不覆盖旧引用。

#### 挂载：父结果只读，子结果独立保存

ContextMount 记录目标 scope、ResourceRef 及固定版本；ResourceRef 可以指向原始资料快照，也可以在 Stage 4 指向不可变结果版本。初版是数据库关系与受控读取接口，不需要操作系统挂载。上下文先提供获准的资源目录，必要内容由 Builder 装配或工具按需读取。

- 父摘要是只读来源，子节点过程保存在自己的工作区，输出单独保存为“便签”。便签可以是完整结果，不要求实现文本差异或自动合并。
- 同级分支默认互不可见；显式挂载也必须通过 ScopeService。父子展示关系不会自动授权资源或继承全部对话。
- 父结果产生新版本时只提示更新，不替换已运行或已完成任务的输入。采纳新版本需要新执行，并保存新 ContextSnapshot。
- 父摘要包含本节点排除的信息时，首版整份拒绝挂载。需要保留其他内容时，从获准材料生成独立、可追溯的过滤版本，经范围检查后挂载；不能先把混合摘要全文给模型再要求忽略。
- 派生摘要保存来源依赖；无法明确拆分归属时按整个摘要的依赖范围判断。缓存、索引、搜索摘要和解析产物同样检查范围，不仅检查原始文件。

#### 范围变化、撤权与恢复

研究主题约束与访问权限分开：前者通过查询约束、材料相关性筛选和独立评测处理；后者由程序强制执行。可验证的隔离承诺是不注入被排除分支的历史、材料与工具返回，不承诺阻止模型用预训练知识提到其他主题。

恢复绑定原输入、资料和研究范围版本，但当前有效访问权限始终优先。资料撤权后，原快照不能继续授权读取；受影响步骤明确阻断，衍生结果也沿来源依赖检查访问。用户在某节点排除资料只改变该节点及受影响的派生执行，不撤销其他独立分支的资料权限。

如果被排除或撤权的内容已经进入模型上下文，停止受影响的在途执行，禁止发布其迟到结果；后续执行重新构建干净上下文，不能原样恢复旧会话或 SDK 检查点。创建挂载、每次读取和结果发布都检查权限/范围是否仍有效。

以下补充来源于本轮文档/源码定向阅读，在线文档与主分支链接未固定提交，不代表已运行验证；实施时固定所选依赖版本。参考边界：GPT Researcher 的 [混合研究](https://docs.gptr.dev/docs/gpt-researcher/context/local-docs) 与 [DocumentLoader](https://github.com/assafelovic/gpt-researcher/blob/master/gpt_researcher/document/document.py) 用于资料接入；[PaperQA 固定版本](https://github.com/Future-House/paper-qa/blob/57e89f7223b0960d5ee5ea048c69e3c47e088572/src/paperqa/docs.py) 用于内容身份与引用元数据；[Docling](https://docling-project.github.io/docling/usage/) 是结构化解析和 OCR 的首个候选，需用实际中文材料验收。[Deep Agents 子 Agent](https://docs.langchain.com/oss/python/deepagents/subagents) 与 [文件后端](https://docs.langchain.com/oss/python/deepagents/backends) 提供独立上下文和按路径读取的参考，但默认共享文件后端不满足本产品的分支隔离；只读版本挂载、授权和发布规则由本产品实现，不因此替换既定 Core 引擎。

#### 节点与两类关系

每个节点包含问题目标、用户指令、挂载清单、运行关联和当前结果指针。公司、报告期等是场景属性，不是通用节点的必填项。Agent 在节点目标内自主规划，用户创建的分支按该分支指令执行；自行生成的计划不能覆盖用户约束。只有可独立续研的子问题形成研究节点，搜索/读取/计算等操作留在节点执行记录中。

| 关系 | 保存内容 | 作用 |
|---|---|---|
| 展示父子关系 | `display_parent_id`，每个非根节点一个父节点，禁止成环 | 表示从哪里分出，组织研究树 |
| 计划执行依赖 | ResearchPlan 中尚待完成的前置步骤 | 决定何时可以开始执行；计划必须无环 |
| 实际输入依赖 | ContextSnapshot 与 NodeResultDependency 中的明确资源/结果版本 | 说明结果用了什么，支持复现、范围检查与更新提示 |

结果 2、3 都可以从结果 1 分出，各自只读挂载“结果 1 v1”。比较结果 4 可在画布上放在结果 1 下，但实际输入是“结果 2 v1＋结果 3 v1”。因此展示是一棵树，实际依赖允许多输入。已有结果版本直接读取；依赖尚未完成的步骤必须等待，完成后先固定版本再执行。不得把“当前最新结果”作为运行中不断变化的输入。

#### 结果版本、状态与命令

NodeResultVersion 发布后不可修改，记录 run_id、context_snapshot_id、指令版本、结果正文/产物和完成情况（完整或部分完成及缺失项）。输入依赖绑定具体版本。后续执行创建新版本，旧成果继续可回看；当前结果指针只有在节点 revision、预期 run_id 及当前权限检查通过时才能更新。正文复用执行层已存内容或不可变产物引用，不复制第二套可变运行输出。

选择状态（selected/excluded）、执行状态（查询关联 run）与更新提示分开表达。上游出现新版本时，只将依赖旧版本的下游标记为“有上游更新／待重新汇总”，不抹去旧结果，也不使它相对原快照变成错误。只有真实输入依赖传播提示，普通父子展示关系不传播。

| 用户命令 | 执行与版本规则 |
|---|---|
| 选择 | 纳入后续计划或比较候选；选择本身不启动执行，也不扩大权限 |
| 排除 | 停止本节点新派发并请求取消在途执行；阻止迟到结果成为当前结果，保留已提交历史；若现有汇总使用了该节点则提示需重新汇总，后续计划移除其输入 |
| 重试 | 新 run_id，沿用失败执行的指令和固定输入；仍须通过当前权限检查，不重复提交旧结果 |
| 续研 | 原节点追加用户目标，显式选定可用上下文，新 run_id、新结果版本；同节点命令排队，实际开始时固定输入 |
| 分支 | 创建新节点，保存新指令并挂载选定上游版本；默认不读取兄弟节点，不修改父结果 |
| 采纳上游新版本 | 新执行固定新版本，旧运行和旧结果保持原输入；不静默替换检查点 |
| 比较／重新汇总 | 显式选择参与的结果版本，生成独立汇总节点或该汇总节点的新版本；保留输入集合和缺失项 |

所有命令携带稳定 command_id 幂等执行。单节点同一时刻只允许一个有效写入运行，独立分支可并行。取消或范围变更使旧运行失去发布资格；其他因新执行而过时、但权限仍有效的结果可保留在运行历史，不自动切换当前结果。排除父节点不隐式删除整棵树，但依赖其被排除内容的后续执行必须重新装配范围。

#### 两个贯穿案例与验收

**案例 1：公司比较。** 用户上传三家公司同一报告期的材料，系统校验期间和口径，分别研究现金流与竞争风险，形成比较表与报告。用户选择一家续研，新结果单独发布，旧比较产物提示该输入有更新；用户发起重新汇总后生成新版本。若排除一家公司，其材料及包含它的混合摘要不得进入被限制的后续节点。Stage 5 补充验收比较结论可以点击到具体原文。

**案例 2：独立探索。** 用户提出想法，Agent 头脑风暴生成结果 1 v1；用户分别指定方向生成结果 2、3。两者都只读挂载结果 1 v1，各自过程与输出独立。结果 2 的唯一标记不得出现在结果 3 的输入或工具返回；修改结果 1 不改变已有两个分支的输入；用户明确要求比较后，结果 4 才同时挂载结果 2、3 的选定版本。创意和假设不强制伪造引用，其中的外部事实与推测需明确区分。

阶段验收必须同时通过：两个案例的输入依赖可查询；同一命令重复提交不产生重复节点/结果；兄弟分支无自动串流；旧结果可回看；迟到结果不覆盖；移动卡片不改变挂载；上游更新只提示、不自动重算。

恢复承诺是步骤级，不是每个 token 级；外部 API 与数据库之间不能凭空实现恰好一次。代码/SDK 检查点版本不兼容时明确拒绝恢复，保留旧成果并新建运行；不为旧状态加入无限兼容层。

10. **故障定位/回退**：计划本身错看 compiler；计划对但执行错看原执行链；指令错误看 SkillResolver 与内容版本。回退 active 指针影响未来实例，旧实例仍绑定旧版本。

### Stage 9 — 长期记忆与偏好

1. **只增加的能力**：在新任务中显式使用可管理的历史信息和已确认用户偏好。
2. **加入时机**：已有上下文装配、反馈来源、可复用方法和基准，才能验证记忆提升了什么；此前不靠自动记忆才能完成研究。
3. **依赖/禁止侵入**：MemoryService 提供带来源的 ContextContribution，由 ContextBuilder 按 scope/预算装配；写入通过明确 MemoryCommand。不能直接改 session、Agent 指令全局变量、事实证据或 active Skill。
4. **新增模块/接口/数据/表**：`memory/service.py`、`preferences.py`、`retrieval.py`；MemoryItem、Preference、MemoryCandidate、ContextContribution。表 `memory_items`、`preferences`；未确认候选可作为 memory_items 的状态保存。记录 user_id、场景、来源事件/证据、有效期、确认状态和版本。
5. **不应修改**：Core、Orchestrator、ResearchService、EvidenceService、模板编译器；通过应用 composition 给 ContextBuilder 增加一个 provider。
6. **参考实现**：先借鉴 Mem0 Memory.add/search 的入口与提取流程，Letta 的作用域和受限父记忆快照。需要基于经历归纳时再评估 Hindsight retain/recall/reflect 与 run_consolidation_job；这些 adapter 到实际需要时才创建。
7. **单独测试**：跨用户/场景污染、明确指令覆盖历史偏好、候选不自动生效、过期/删除/纠正、来源缺失、召回无结果。用固定偏好库比较开启/关闭的 PreparedInput 差异；真实模型测试是否真正按偏好工作。
8. **回归测试**：C0–C8；关闭记忆时基线不变；开记忆后 scope/证据质量测试不降低。偏好可以调整分析次序，不能隐藏反证或把过去结论当本次事实。
9. **真实交互**：明确保存“公司研究先看现金流”；新建会话自动应用并展示记忆来源；本次要求先看竞争格局时覆盖旧偏好；删除后不再应用。
10. **故障定位/回退**：错误内容写入看 MemoryCommand/抽取；正确记忆没找到看 Retrieval；找到但未传入看 Builder；传入但未遵守看 Agent。停用 provider 后基础研究不读取记忆。外部记忆服务故障不允许静默扩大查询或伪造召回。

Graphiti 暂不属于这一阶段的必需依赖。若未来要研究企业关系和事实有效时间，可用独立 FactKnowledgeService 包装 EpisodicNode/EntityNode/EntityEdge；它仍不能与用户偏好合为一种数据。

### Stage 10 — 经评测的 Skill/workflow 进化

1. **只增加的能力**：自动提出方法改进候选，经验证与发布流程影响未来任务。
2. **加入时机**：Stage 7 给评价依据，Stage 8 给稳定版本资产。Stage 9 可提供额外偏好信号，但进化不必依赖通用记忆系统。
3. **依赖/禁止侵入**：CandidateGenerator 消费获准的反馈/轨迹；EvaluationService 在冻结样本执行候选；VersionPublisher 经受控接口切换 active 指针。不能修改 Core 源码、任意工具实现、scope规则或生产中间状态。
4. **新增模块/接口/数据/表**：`evolution/candidates.py`、`gates.py`、`publisher.py`；EvolutionCandidate、EvaluationManifest、PromotionDecision。表 `evolution_candidates`、`promotion_decisions`；复用已有版本和评测表。
5. **不应修改**：Core、SDK adapter、研究状态机、证据与范围服务、workflow 执行语义；候选首先只修改受约束的方法内容和模板参数/结构。
6. **参考实现**：BearCode OnlineSkillCandidate/online_ingest/_freeze_replay_pool/_promotion_decision；Langfuse 数据集与评测；Letta ReflectionMemoryWorktree 的候选隔离与整合生命周期。无需把其完整实现搬入。
7. **单独测试**：生成候选不影响 active；冻结测试材料与版本；拒绝引用/范围退步、成本超限；拒绝缺失评测或比较基线改变的发布；并发发布使用 compare-and-swap；回退版本指针有效。
8. **回归测试**：C0–C9；候选跑同一固定输入与资料快照，同时覆盖留出任务；所有硬约束先通过再评价偏好收益。发布前后基础 Core 的代码与原测试不变；运行中任务继续使用原版本。
9. **真实交互**：看到“把现金流检查提前”的候选差异、关联反馈、与旧版对比的质量/成本；确认启用后新任务使用，回退后新任务恢复旧版。
10. **故障定位/回退**：候选不合理看 Generator；测分异常看数据/评分器；发布了不达标版本看 Gate/Publisher；发布后执行计划不符看 Compiler/Resolver。关闭进化仅停止候选与发布，已确认方法继续运行。

## 四、每次增加能力的测试与发布门槛

配套方案：[研究 Agent 评测框架与落地方案](</Users/chenyouran/Documents/ChatGPT/New project 2/architecture-analysis/研究Agent评测框架与落地方案.md>)。该方案依据两份评测笔记，细化八维指标、task/trial/outcome、Grader、Oracle 与负对照、首批任务、多次运行统计及阶段发布门槛。

### 测试分层

1. **模块单元测试**：纯函数、状态机、作用域、参数编译、引用关系；无需模型和网络。
2. **接口契约测试**：同一个测试套件验证内存/SQL repository、脚本/OpenAI adapter 的归一化行为。真实厂商协议差异在各 adapter 的映射测试验证。
3. **组合测试**：新能力+相邻模块；验证数据是否经过公开接口，不能直接读内部状态。
4. **回归场景**：保留每个阶段的最小真实业务场景。C0–Cn 是逻辑集合，实际避免重复跑完全相同的测试。
5. **故障注入**：工具失败、数据库提交失败、重复命令、超时和进程中断。Stage 6 之前不声称能通过真正的恢复测试。
6. **真实模型评测**：固定模型配置、提示/Skill版本、资料快照和场景；比较工具选择、证据支持、范围遵守和成本。模型测试具有随机性，报告次数与结果分布，不用一次跑通证明“永不回归”。

### 每个阶段的最小发布检查

- 新模块的单独测试通过。
- 累积的确定性回归与接口契约通过。
- 新模块关闭时，基础 Agent 场景可运行。
- 必需前置模块缺失时，对应入口明确不可用，不放宽规则。
- 演示交互可从全新测试数据完成，失败能通过运行 ID 定位。
- 新模块没有要求 Core 引入任何业务类型或外部平台依赖。
- 实际实现完成后运行适合本阶段的真实模型小样本；没有评测数据就不宣布质量改进。

### 可回退的具体含义

- 新服务注册、工具包装与 provider 注册集中在 composition，禁用后卸载相应入口及依赖它的能力。
- 保留正常保存的数据和结果；关闭模块不做破坏性删表。
- 版本回退是切换受管理的 Skill/workflow active 指针，不是保留多套旧业务代码。
- 当前实现不再使用的代码路径应删除；不为历史数据自动建立越来越多的兼容分支。
- 对无法由当前代码读取的检查点明确报版本不匹配；保存可读成果，新建执行。不要通过重置状态或忽略错误伪装恢复成功。

## 五、故障定位的统一路径

```text
user_command_id
  → research_node_id（若有）
  → run_id / parent_run_id
  → context_snapshot_id（若有）
  → workflow_id / step_id / attempt（若有）
  → tool_call_id
  → source_snapshot_id / evidence_id（若有）
  → result_version
  → feedback / evaluation / skill_version（若有）
```

所有模块保留自己的领域对象；上述 ID 只是关联键。基础 Core 事件只需要 run/tool/parent ID，其他模块通过 run_id 丰富关联信息，不把全部业务字段塞回 Core。

排查次序：命令是否正确 → 输入范围是否正确 → 调度对象是否正确 → 工具返回是否正确 → 结果引用是否正确 → 状态提交是否正确 → UI投影是否正确 → 模型生成是否满足目标。先区分确定性软件错误与模型质量问题。

## 七、实施建议

每次只完成一个阶段，交付四样东西：**可运行入口、明确接口、最小测试集、真实交互演示**。阶段验收通过后再增加下一项能力。

第一个产品里程碑建议设在 Stage 5：已经具备可选分支、独立范围和可回查证据的研究树。Stage 6 让它跨进程可靠运行；Stage 7–10 逐步形成质量改进与进化闭环。

不要用“未来可以替换”作为今天增加抽象的唯一理由。只有模型运行、存储、执行调度和外部平台等明确边界需要 adapter；内部业务逻辑直接用小型 service 与值对象。Core 稳定性的验收标准是后续新能力不要求修改其循环、引入领域类型或读取其内部状态，而不是宣布它从此绝不允许修复缺陷。
